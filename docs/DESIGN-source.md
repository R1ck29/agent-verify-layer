# ハーネス検証レイヤー設計

Nov 18, 2026 · @Riku Suzuki

## 要約

記事の原則のうち、ハーネスに入れるのは次の 5 つです。どれも条件がそろったときだけ動くので、常時かかるトークン費用は増えません。

1. **verify の実行は標準機能に任せる**：Claude Code v2.1.286 以降は、リポジトリに `verify` スキルがあれば、コミット直前に実行するよう Claude に指示が入る。ハーネスは、各リポジトリにこのスキルを用意する手順と、条件が崩れていないかの確認を受け持つ
2. **コミット時の関門**：そのファイル状態で verify が実行されたかを記録する（観察モード）。標準の仕組みは指示であって強制ではないので、守られているかをここで測る
3. **diff で発火するチェックリスト**：過去の障害から作った項目のうち、diff が当てはまる 3〜10 件だけを確認する
4. **レビュアーは 1 体**：同梱の `/code-review` を主レビュアーに決め、増やさずに鍛える
5. **チェック自体の採点**：レビュアーとチェックリストを Agent Harness Eval で、実際のバグの正解キーを使って採点する

設計の方針は 4 つです。

- 合否は終了コード、ハッシュ、diff などの決定的な材料で決める。モデルの判断は検査の中身にだけ使う
- チェックリストは作業ツリーではなく HEAD から読む。変更が、自分を判定するチェックを書き換えられないようにするため
- 新しく作るのは、関門の hook とチェックリストの照合スクリプトだけにする。verify の中身、起動手順、レビュー本体は同梱の仕組み（`/verify`、`/run-skill-generator`、`/code-review`）に任せる
- データ抽出（SQL）にも同じ考え方を当てる。小さな範囲で実際に実行して結果を検査するのが E2E、不変条件の確認がプロパティテスト、旧クエリとの結果比較が差分テストにあたる

初版では自作の `verify-change` スキルが verify を実行する案でした。同梱の `/verify` と役割が重なり、標準の指示の仕組みで足りることが分かったため、取りやめました。

## 前提

記事の仕組みのうち、REVIEW.md の読み込みはこの環境では使えません。読むのは GitHub 上の管理型 Code Review だけで、この環境からは GitHub に届きません。一方、「コミット前に verify を走らせる」部分は Claude Code の標準機能で賄えます。

### 公式ドキュメントで確認したこと（2026-11-18 時点）

| 対象 | 確認した事実 | 設計への影響 |
| --- | --- | --- |
| コミット前の verify 指示 | v2.1.286 以降、セッション開始時に `verify` か `simplify` という名前のスキルがあれば、コミット直前に実行するよう Claude に指示が入る（ドキュメントとテストだけの変更は除く）。対象はエンタープライズ・個人・プロジェクトなどのスキルで、同梱版・プラグイン・claude.ai のスキルは対象外。`disable-model-invocation: true` や `includeGitInstructions` の無効化で指示は消える | verify の実行はこれに任せる。プラグインで配るスキルでは条件を満たせない |
| `/verify` | ユーザーが呼んだときだけ動く（v2.1.215 以降）。手順の記録がなければ `.claude/skills/verify/SKILL.md` に書き、リポジトリ直下では同梱の `/verify` を置き換える。この記録はプロジェクトのスキルなので、上の指示の対象になる | 各リポジトリで 1 回 `/verify` を実行して記録させる |
| `/run-skill-generator` | 起動手順を `.claude/skills/run-<name>/` に記録し、`/run`・`/verify`・その他のエージェントがそれに従う | 名前が `verify` ではないので、これだけでは指示の対象にならない |
| 同じ名前のスキル | エンタープライズが個人より、個人がプロジェクトより優先。プラグインのスキルは名前空間つきで衝突しない | 個人用の場所に `verify` を配ると、リポジトリの記録を上書きする |
| `/code-review` | どのプランでもセッション内で動く。背景の subagent で実行。CLAUDE.md に従い、REVIEW.md は読まない。`ultra` は その推論経路では使えず、ローカルのレビューに切り替わる | 主レビュアーに使える。「何を重視するか」は CLAUDE.md とチェックリストで渡す |
| 管理型 Code Review | REVIEW.md で調整する GitHub PR 向けのサービス | 使えない。「ベースから読む」原則だけを自前で実装する |
| `/goal` | 中身はセッション単位のプロンプト型 Stop hook。評価は small fast model。ツールを呼ばず、会話に出たものだけで判定する | 長い作業で利用者が明示的に使うものとし、常設はしない |
| Stop hook | 間にツール呼び出しがないまま 8 回連続でブロックすると上書きされる | 完了判定には使わない |
| hook の `if` | permission ルールの形で絞れる。`Bash(git commit *)` や `Skill(verify)` のように書け、ツールのイベント（PreToolUse・PostToolUse など）で使える。Bash の判定はベストエフォート | 関門と verify 実行の記録は hook でよい。確実な禁止が要るものは permission で行う |
| UserPromptExpansion hook | 利用者が打ったコマンドが展開されるときに発火し、コマンド名で絞れる | 利用者が自分で `/verify` を打った場合も記録できる |
| Windows の hook | シェル形式は Git Bash が必要。`"args": []` の exec 形式ならシェルを通さずに起動できる | スクリプトは Node の 1 本で書き、exec 形式で呼ぶ |
| hook の入力 | すべてのイベントに `session_id` と `cwd` が入る | 「1 セッションで 2 回止めたら通す」を実装できる |

### 既知の導入先制約

- 推論は `CLAUDE_CODE_USE_BEDROCK` 経路、この環境から GitHub は使えない
- 開発環境は macOS のみで、Windows は手元で試せない
- モデル費用は月額の上限あり。常時かかる費用は禁止、プロンプト本文はログに残さない
- 利用者はエンジニアと非エンジニア。プロファイルごとに配布物が異なる
- Skills・Subagents・Hooks はプラグインで、Rules と MCP 設定は直接配布する
- PR はほぼ使わず、直接コミットが中心

## 構成要素の詳細

新しく作るのは、Node のスクリプト 2 本（`gate.js`、`checklist.js`）と hook の設定だけです。どちらも分岐のない 1 本のコードで、Windows と macOS の両方に対応します。

### 1. verify（リポジトリの記録と標準の指示）

verify の実行は Claude Code に任せます。ハーネスが受け持つのは次の 3 つです。

1. **導入手順を配る**：各リポジトリで 1 回 `/verify` を実行し、記録された `.claude/skills/verify/SKILL.md` をコミットしてもらう。`/run-skill-generator` の記録（`run-<name>`）だけでは名前の条件を満たさない
2. **条件を確かめる**：インストーラの更新時に、Claude Code が v2.1.286 以上か、配布設定で `includeGitInstructions` を切っていないか、記録されたスキルに `disable-model-invocation` が付いていないかを確かめる。毎回のセッションでは行わない
3. **書き込まない**：`.claude/skills/verify/` は `/verify` が自分の記録として使う場所なので、ハーネスからは触らない

**実行の記録。** verify が実行されたときの作業ツリーのハッシュを、hook で `.git/claude-verify/runs/<tree>.json` に残します。

- Claude が呼んだとき：PostToolUse、`matcher: "Skill"`、`if: "Skill(verify)"`
- 利用者が `/verify` を打ったとき：UserPromptExpansion、matcher は `verify`
- ツリーハッシュは、一時インデックスに `git add -A` して `git write-tree` で求める。書くのは時刻と経路だけで、プロンプトも出力も書かない。`.git/` の下なので、コミットにも配布物にも入らない
- 分かるのは「実行された」ことだけで、通ったかどうかは分からない。verify のあとに 1 文字でも変えればハッシュが変わり、記録は無効になる。記事の「古いコミットのレビューは役に立たない」をこの形で実現する

**3 回で人を呼ぶ。** 成否を数える自作スクリプトがなくなるので、Rules に一文で書きます（第 6 項）。守られているかは、台帳の「1 コミットあたりの verify 実行回数」で見ます。

### 2. コミットの関門（PreToolUse hook）

- **発火**：`matcher: "Bash"` と `if: "Bash(git commit *)"`。exec 形式で `node gate.js` を呼ぶ
- **処理**：今の作業ツリーのハッシュで実行の記録を探し、結果を台帳 `.git/claude-verify/ledger.jsonl` に書く。結果は verified（この状態で実行済み）、stale（実行後に変更あり）、none（未実行）、skipped（ドキュメントとテストだけの変更。標準の指示も対象外）
- **コミット後**：同じ条件の PostToolUse で `git rev-parse HEAD` を台帳の行に足す。未検証のコミットを SHA で引けるようになる
- **テレメトリ**：件数だけを OTEL に送る（結果ごとの数、止めていたはずの数、1 コミットあたりの verify 実行回数）。Agent Harness Eval v0.5 が集める「内容を含まない信号」にそのまま足せる

モードは配布マニフェストのプロファイルごとに持ち、直接配布する設定ファイルで切り替えます。

| モード | 動き |
| --- | --- |
| off | 何もしない |
| observe | 止めずに「止めていたはず」を台帳に記録する。誤検知を、誰かに影響が出る前に見つける |
| enforce | stale と none を deny する。理由には「verify を実行するか、実行しない理由を `Unverified-Reason:` としてコミットメッセージに書く」を返す。同じ `session_id` で 2 回止めたら、3 回目は通して none と記録する |

### 3. diff で発火するチェックリスト

リポジトリごとに `.claude/verification/checklist.yaml` を置きます。各項目は、発火条件（パスの glob と diff の正規表現）、確認すること（ 1 文）、元になった不具合を持ちます。

- `checklist.js` は `git show HEAD:.claude/verification/checklist.yaml` で HEAD 側を読み、`git diff HEAD` と突き合わせて当てはまる項目だけを出す。作業ツリー側のチェックリストは使わない
- 実行の記録と同じ `Skill(verify)` の hook から呼び、当てはまる項目を `additionalContext` で Claude に渡す。当てはまる項目がなければ何も渡さないので、トークンは増えない
- `/code-review` のレビュアーには渡せない（CLAUDE.md しか読まない）。レビュアーに必要なものは、CLAUDE.md の短い節に書く
- 変更がチェックリスト、CLAUDE.md、hooks、`.claude/skills/verify/` を触っていれば「チェックを変える変更」として出し、人の確認を求める

最初の項目は、ハーネス自身の過去の不具合から作ります。

| 発火条件 | 確認すること | 元になった不具合 |
| --- | --- | --- |
| hooks の変更で stderr への出力が増える | モデルや利用者に届けたい通知が stdout（または JSON）に出ているか | strategic-compact の通知が約 4 か月 stderr に出ていた |
| 更新先の振り分け（classifyDestination）の変更 | agents・rules が黙って更新されない経路がないか | 振り分けの誤りで更新が黙って失敗した |
| マニフェストへのタグやキーの追加 | コードから参照されているか | 段階配布用の tier タグがどこからも参照されていなかった |
| 案内文やガイダンスの追加 | モデルに届く経路（読み込み・注入）があるか | F1 oracle の案内がモデルに届いていなかった |
| git\_commit の更新処理の変更 | 条件なしで更新していないか | git\_commit の無条件更新（記録済み・未修正） |
| 配布設定の変更 | `includeGitInstructions` を切っていないか。`verify` という名前のスキルを配っていないか | この設計の前提条件 |
| テストファイルで skip・sleep・リトライの追加 | flaky なテストを隠していないか | 記事の規則 |

### 4. レビュアーは 1 体

主レビュアーは同梱の `/code-review` にします。理由は 3 つです。

- その推論経路でもセッション内で動く
- ドキュメント上は、会話履歴を持たない subagent で動く。「独立レビューには実装の文脈を渡さない」という既存の学びと合う（実機で要確認）
- レビューの中身を自分で保守しなくてよい

重視する点は CLAUDE.md の短い節で渡します。REVIEW.md は作りません。既存のレビュー系（自作のレビュー subagent や CRG を使うレビュー）は、評価で `/code-review` より良いと示せなければ順に外します。2 体目は足しません。

自作に置き換えるのは、第 5 節の評価で取りこぼしが特定の種類に偏っていると分かったときだけです。そのときは `code-review` という名前のスキルで置き換えます。同梱のコマンドは置き換わりますが、別名の `/review` は同梱のまま残ります。

### 5. データ抽出向けの verify（データ抽出の利用者だけ）

SQL のリポジトリには起動するアプリがないので、`/verify` の記録は向きません。代わりに、SQL 向けの `verify` を個人用の場所 `~/.claude/skills/verify/` に直接配ります。個人用のスキルは標準の指示の対象になります。

ただし、個人用はプロジェクトより優先されるので、エンジニアに配るとリポジトリの記録を上書きします。配るのはデータ抽出の利用者のプロファイルだけにします。

中身は、記事の 3 種のテストをクエリに当てはめたものです。「条件を間違えたクエリが、黙って欲しいものと違うデータを返す」問題への対策です。

| 記事のテスト | クエリでの形 | 例 |
| --- | --- | --- |
| E2E | 小さな範囲で実際に実行し、依頼文の条件と結果を突き合わせる | 1 パーティションで実行し、期間・対象・件数が依頼と合うか |
| プロパティ | 結果が必ず満たす性質を確かめる | 主キーの重複なし、金額が負にならない、日付が依頼期間内、NULL 率が想定内 |
| 差分 | 旧クエリと新クエリを同じデータで実行して比べる | 修正の前後で件数と合計の差を出し、意図した差か確認する |

- 「正しい結果」の条件は依頼文から作る。依頼が曖昧なら、実行前に利用者に確認する（既存の方針どおり）
- 小さな範囲の試行をどこで流すか（Trino で同じテーブルに届くか）は要確認
- クエリが git 管理なら、同じ記録と関門を使う。管理外なら関門はかけず、確認結果を回答に添えるだけにする

### 6. Rules に足す 2 行

- flaky なテストを skip、sleep、通るまでの再実行で済ませない。原因が分からなければ削除し、理由をコミットメッセージに書く
- verify が続けて失敗したら、2 回目は Opus に原因調査を渡し、3 回目は作業を止めて人に報告する

## チェック自体の検証

レビュアーとチェックリストは、Agent Harness Eval の新しいタスク群（family は `review-recall`）として採点します。変更を配布するのは、v0.5 の関門を通ったときだけです。

### 例題の作り方

1. **正例**：ハーネスのリポジトリで、不具合を入れたコミット（あとで fix や revert されたもの）を探す。その直前の状態を再現し、不具合を入れた変更をレビューさせる
2. **正解キー**：バグを 1 文で書く。指摘がその 1 文の内容を正しく説明しているときだけ得点にする
3. **対照**：その後問題が出ていない変更を、正例と同じくらいの大きさで選ぶ。ここでの指摘は誤検知として数える
4. **分割**：v0.5 の train / dev / holdout を使う。調整は dev までで行い、holdout は配布前の判定にだけ使う

### 測るもの

- 再現率：正例のうち、正解キーの不具合を指摘できた割合
- 誤検知：対照で出た指摘の数
- チェックリストの効き：同じ正例を、チェックリストありとなしで比べた再現率の差

調整は、dev での改善が holdout で出なくなったら止めます。このハーネスでは、調整したシナリオで 100% だった評価が、新しいシナリオで 0% になったことが実際にありました。

### 件数が少ないうちの扱い

今分かっているハーネスの不具合は 5 件ほどで、符号検定で判定できる件数には足りません。そのため当面は `promote` で判定せず、「どの不具合を取りこぼしたか」の記録として使います。証跡の台帳と第 6 節の仕組みで例題が増えてから、統計的な判定に切り替えます。

費用は 1 例ごとにレビュー 1 回分です。月 1 回、自分の環境で回し、AHE の月額上限（`--monthly-budget-usd`）の範囲で抑えます。

## 見逃しをルールに変える

見逃しの入口は 3 つです。どれも、人が承認したものだけがチェックリストに入ります。PR をほぼ使わないので、記事の「人のレビューコメント」の代わりに fix コミットと revert を使います。

1. **パターンの掘り起こし（月 1 回）**：直近の fix と revert から、不具合を入れたコミットを特定する。同じ種類の問題が 2 件以上あり、diff から検出できるものを候補にする。候補はエージェント 3 体に反証させ、残ったものを人が承認する
2. **再現**：既知の不具合ごとにレビュアーを 3 回走らせる。2 回以上見つければ「検出できる」。小さな diff なのに見逃したものは、チェックリストに足す候補にする。結果は第 5 節の例題にもなる
3. **台帳から**：関門の台帳で none のまま入ったコミットがあとで fix されていれば、優先して 1 と 2 に回す

### 刈り込み

- 各項目の「発火した回数」と「それで問題が見つかった回数」を、件数だけテレメトリで集める。チェックリストのファイル自体には書かない（書くと余計な diff が出る）
- 削除の判断は既存のテレメトリ方針に従う。発火する機会があった回数を分母にし、一定期間一度も役に立たなかった項目を候補にする。期間はまず 6 か月で始め、実績を見て決める
- 削除も人が承認する。Rules と CLAUDE.md のテスト関連の行も、同じ時に見直す

利用者の種類ごとに、最終的に配るものは次のとおりです。

| --- | --- | --- | --- |
| 自分 | リポジトリに記録 | observe から enforce | ハーネスのリポジトリに置く |
| エンジニア | リポジトリに記録 | observe から enforce | リポジトリにあれば使う |
| データ抽出の利用者 | 個人用の SQL 向けを配る | クエリが git 管理のときだけ observe | なし |
| 非エンジニア | なし | off | なし |

## 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| Stop hook で毎ターンテストを回す（記事の例） | Stop は質問だけのターンでも毎回発火する。時間がかかり、常時の費用を禁じる方針に反する。確認はコミット時に寄せる |
| プロンプト型・エージェント型の Stop hook で完了を判定する | 毎ターンモデルを呼ぶので常時の費用になる。エージェント型 hook は実験的機能 |
| `/goal` を常設する | セッション単位で、利用者が条件を書く仕組み。長い作業で使う案内だけにする |
| REVIEW.md を作る | ローカルの `/code-review` は読まない。読むのは GitHub の管理型サービスで、この環境では使えない |
| レビュアーを重ねる（`/code-review`、自作 subagent、CRG） | 記事では 2 体目を足すより 1 体目を改善するほうが効いた。費用も倍になる |
| permission でコミットを禁止する | 「理由を書けば通る」「2 回止めたら通す」という通り道を作れない。この関門は記録と促しのためのもの |
| hook でコミットメッセージに trailer を書き足す | `git add ... && git commit` のような連結コマンドで壊れやすい。SHA と台帳の対応で同じことができる |
| 証跡をセッション ID で結びつける | 確認したあとの編集を見逃す。作業ツリーのハッシュで結びつける |
| 同梱の `/code-review` をすぐ自作で置き換える | 保守の負担が増える。評価で取りこぼしの偏りが見えてからにする |
| 自作の verify-change スキルで verify を実行する（初版の案） | 同梱の /verify と役割が重なる。プラグインのスキルは標準の「コミット前に実行」の指示の対象外で、指示の仕組みで足りる |
| CLAUDE.md に「毎回 verify を使って」と書く | 同梱の /verify はユーザーが呼んだときだけ動く。リポジトリに記録があれば標準の指示が入るので、書く必要もない |
| エンジニアにも個人用の verify を配る | 個人用はプロジェクトより優先され、リポジトリごとの記録を上書きしてしまう |

## 未検証・要確認

次の 12 点は、ドキュメントだけでは確かめられていません。フェーズ 0 と 1 の中で、導入先の実機で確かめます。

- [ ] 導入先の Claude Code が v2.1.286 以上か。配布設定で `includeGitInstructions` を切っていないか
- [ ] `run-<name>` の記録がすでにあるリポジトリで、`/verify` が `.claude/skills/verify/SKILL.md` を作るか
- [ ] 記録された `verify` を、標準の指示どおり Claude がコミット前に実際に呼ぶか（呼ばれる割合は台帳で測る）
- [ ] `if: "Skill(verify)"` の PostToolUse と、`/verify` を打ったときの UserPromptExpansion が、どちらも実際に発火するか
- [ ] PostToolUse の `additionalContext` で、チェックリストの項目が Claude に届くか
- [ ] 導入先の Claude Code の版と その推論経路で `/code-review` が動き、会話履歴なしで走るか
- [ ] `/code-review` は背景で動くので、指摘が届く前にコミットが進まないか
- [ ] `if: Bash(git commit *)` が、Claude の実際のコミットのどれだけを拾うか（`git -C` など）。観察期間に台帳と `git log` を突き合わせて測る
- [ ] Git Bash のない Windows 端末で、exec 形式の Node の hook が動くか
- [ ] 一時インデックスでのツリーハッシュ計算が、大きなリポジトリで何秒かかるか
- [ ] データ系の小さな試行をどこで流すか（Trino から同じテーブルに届くか）
- [ ] 台帳の件数を OTEL で集めてよいか（v0.5 の「利用者から何を集めてよいか」と同じ導入先確認）
