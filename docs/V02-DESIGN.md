# Verify v0.2 設計 rev5

v0.2 は、コード変更を終える前に、利用者の依頼から実装が誤っている可能性が最も高い境界入力を探し、公開入口で試す。最初の実装は Linux 上の Claude Code と Codex、`pytest` と `node --test` に絞る。ランナーは fixture ごとに明示する。敵対的な見直し、ランナーの汎用自動検出、Windows 対応は後段に回す。

## 改訂履歴

- rev2 — 初回の astra レビュー 5 件を反映（§5）。
- rev3 — ランナー設定の新設を保護対象に含め、既存の公開テストの新規回帰を依頼の最終判定に反映。`verifyV2.mode` 省略時の既定値を明記。
- rev4 — 開始時に合格した既存の公開テストの変更後結果を照合できない依頼は「未検証」とし、自動テストの終了例を追加。
- rev5 — Opus のブロッキング 6 件に対応。境界選定、隔離実行、assertion の記録、意図した変更、外部採点、P2 の事前登録を具体化（§5）。

## 1. v0.1 で分かったこと

E1b（旧 dev の罠 6 件と対照 4 件）の Claude の罠では P0 9/12、P1 10/12、P2 9/12 だった。P2 で verify スキルが呼ばれたのは 4/12 で、コミット後の hook は観察モードで記録するだけだった。Codex は P2 の全 6 試行で `mark verify` が実行されたが、P1 と同じ 5/6 だった。テストを複数回実行した試行でも、依頼された振る舞いの境界を確認できていなかった。また、旧 P0 は fixture 内の verify スキルを参照できた。

最初の評価では、層を外した今回の P0 と、終了前に追加テストを求める P2 を比べる。旧 dev の成績は経緯として扱う。

## 2. 最小版の仕様

### 2.1 終了時の介入

- 対象は、依頼開始時から終了時までに対象コードの差分がある依頼。コミットの有無を問わない。ドキュメントだけの変更は対象外とする。
- 利用者の依頼を受けた時点で、セッション間でも衝突せずファイル名に使える依頼 ID を発行して変更前の状態を保存する。Stop hook による継続では同じ ID を使う。次の利用者の依頼で初めて ID を更新する。依頼開始を識別できない場合は強制モードの有効化条件を満たさない（§3.3）。
- 対象の依頼の最終判定では、現在のスナップショットに対応する追加ケースの有効な証拠と既存チェックの前後の結果を照合する。両方の記録があり、開始時に合格した既存の公開テストすべての変更後の個別結果を照合でき、かつ新規回帰（§2.2）がなければ「検証済み」とする。個別結果を照合できないテストがあれば、追加ケースが合格していても「未検証」とし、照合できない理由を記録する。新規回帰があれば、追加ケースが合格していても「未検証」とし、失敗した公開テストの識別子と失敗理由を記録する。
- `enforce` で現在の状態が「未検証」の場合は、Verify が発生させる追加ターンを **1 依頼につき最大 1 回**に制限して、§2.2 の手順と判明している失敗理由を Stop の理由として渡す。Stop の理由と SKILL には「実装が誤っている可能性が最も高い入力を探して試す」と書く。ブロックを返す前に依頼 ID 単位で介入済みを記録する。再検証は同じ追加ターン内で行える。
- 未検証の原因が依頼を満たすために必要な変更である場合、Stop の理由と SKILL は、その変更を維持し、依頼の該当箇所と具体的な失敗・照合不能・保護差分を残して「未検証（意図した変更）」で終了するよう伝える。既存テストの期待値と依頼が矛盾する場合は、該当テストと矛盾を報告するだけとし、依頼された実装と既存テストをそのまま残す。最終 Stop はその報告を同じ依頼 ID と最終スナップショット ID の未検証理由に結び付ける。§2.4 の保護検査と証拠の条件は引き続き適用する。
- `stop_hook_active` が真なら、他の Stop hook が継続させた場合も含めて、Verify はブロックしない。これが真でも偽でも、介入済みの依頼への再ブロックは行わない。追加ターンでテスト後に実装を直した場合は、修正後の状態に有効な証拠があるかを最終 Stop で照合する。証拠がなければ「未検証」と記録する。
- `observe` は終了時の状態だけを記録する。`off` は v0.2 を無効にする。hook が失敗した場合は継続を要求せず、記録できる場合は「未検証」と失敗理由を残す。観察・強制の両方で「未検証」とともに、確認できた理由（証拠なし、状態の変化、実行失敗、予算打ち切りなど）を記録する。外側の実行器による打ち切りは実行器にも残す。v0.1 を配備した環境では、そのコミット hook は従来の記録用とする。

### 2.2 依頼から証拠を作る

1. ケース JSON ごとに境界候補を **3〜5 件**列挙する。各候補には候補 ID、依頼の該当箇所、具体的な入力、境界の種類（入力の大きさや形、文字や表記、処理順、失敗時の応答など）、現時点の実装に明示的な処理があるかを記す。バグ報告に再現条件があれば最初の候補にする。明示的な処理がない候補や、依頼から期待値が一意に定まる候補を優先し、依頼または許可された公開仕様から期待値を定められる候補のうち、実装が誤っている可能性が最も高いものを選ぶ。選んだ候補 ID、選定理由、公開入口と実際の呼び出し方、入力、期待値、対応するテスト識別子を JSON に記す。依頼の例または既存の公開テストと同じ入力なら `nonBoundary` を記録する。実行器でも具体値を照合できる範囲で同じ印を付ける。
2. 公開入口を実際に呼び、観測結果と期待値を比較する assertion を持つ標準のテストを書く。追加ファイルには依頼 ID を含む一意名 `test_vl_<id>_*.py` または `*.vl-<id>.test.js` を使う。ケース JSON にテストファイルの相対パス、比較の位置、読み込み元を確認する対象モジュールを記す。追加テストが要求との不一致を検出したら、期待値を弱めず実装を直し、最終状態で実行し直す。既存のテスト、共通 fixture、テストの発見や実行に関わる設定は §2.4 に従って保護する。
3. `vl.js verify-diff --case <JSON>` は、指定した同じ追加テストを前後の隔離コピーで実行する（§2.3）。`--case` は最大 3 件まで繰り返せ、同じ追加ターンで計 1〜3 ケースを試せる。再実行は同じケースとして数える。ケース JSON の候補数・必須項目・選定先を検査し、合否はランナーの結果と assertion の記録から判定する。各側の実行件数、指定ケースの状態、終了結果を保存する。変更後は、対象ケースが実行され、指定の assertion を通過し、ランナーもそのケースの成功を報告した記録が必要。収集だけ、0 件、skip・todo・xfail、途中終了、assertion 到達なしは未検証とする。

   - pytest は新しい `__pycache__` のないコピーを使う。Verify がコピー外の自前のプラグインを `-p` で明示的に読み込み、`-o enable_assertion_pass_hook=true` を付ける。プラグインは対象テストの `pytest_assertion_pass` を assertion の位置ごとに数え、指定の比較をテスト識別子と位置で照合する。変更前の不一致は指定の比較で発生した失敗を call フェーズの結果から確認する。テストファイルには標準の `assert` を書く。
   - `node --test` は対象テストのコールバックの先頭で `t.plan(n)` を宣言し、期待値の比較に `t.assert.*` を使う。SKILL にこの規約を記載する。初版の追加ケースでは `n = 1` とし、指定の比較が plan で数える唯一の操作であることを確認する。比較失敗はそのままランナーに伝える。コピー外の reporter がテスト識別子ごとの結果を記録し、plan を満たした成功を assertion 通過の証拠にする。変更前の不一致は指定の比較からの失敗を reporter の結果と照合し、plan 未達や起動失敗と区別する。
   - 追加テストファイルは Verify 専用のヘルパーや記録コードを必要とせず、通常のランナーでも実行できる。
4. 変更前の結果は次のように扱う。公開入口の不在は対象の入口を直接確認して分類する。一般の import 失敗や起動エラーは実行エラーに含める。

   | 変更前の結果 | 証拠としての扱い |
   |---|---|
   | 対象の assertion が期待値との不一致を検出 | 変更後に同じ assertion が合格すれば、その境界で起きていた不一致を確認できる |
   | 公開入口なし | 変更後の合格と合わせて、入口の追加と変更後の振る舞いを確認できる。境界の不具合を変更前に再現できたとは扱わない |
   | 収集・依存関係・実行環境などのエラー | 変更前の比較は未検証 |
   | 期待値に一致 | 変更後の振る舞いは観測できたが、そのケースで変更による差は未検証 |

5. `nonBoundary` のケースは実行結果を残し、境界の証拠から外す。対象モジュールの読み込み元を前後で確認でき、変更後に assertion が合格し、変更前が「期待値との不一致」または入口の追加を求める依頼での「公開入口なし」なら、選んだケースを検証済みとする。依頼には最終状態で有効な境界ケースが少なくとも一つ必要で、その状態で実行した他の追加ケースに要求との不一致が残っていれば未検証とする。
6. 依頼開始時点と変更後の隔離コピーで同じ既存の公開テストを同じ条件で実行する。開始時点で合格したテストが変更後に失敗したら、残りの予算内で同じ条件の新しい変更後コピーにそのテストを指定して 1 回だけ再実行する。両回の結果を記録し、再実行でも失敗すれば新規回帰、合格すれば不安定なテストとして報告する。予算不足で確認できない失敗、収集エラー、モジュール読み込み失敗、ランナー異常終了、件数の不一致などで、開始時に合格したテストの変更後の個別結果を確定できない場合は、理由を記録し、依頼を「未検証」とする。既存チェックと追加ケースそれぞれの結果を同じ依頼 ID と前後のスナップショット ID に結び付け、依頼の最終判定は §2.1 に従う。

### 2.3 前後のスナップショットと台帳

- **変更前**は、利用者の依頼を受けて作業を始める時点の作業ツリー。開始時点にあったステージ済み・未ステージの変更、Git の除外設定に該当しない未追跡ファイルに加え、開始前に `includePaths` で対象に指定したファイルは Git の除外設定にかかわらず含める。作業ツリー上の内容で固定し、利用者の変更を退避・初期化せず、依頼途中のコミットでも基準を更新しない。取得に失敗した場合は比較を未検証とする。
- **変更後**は、検証コマンド実行時に同じ規則で採取した作業ツリー。未コミットの実装と未追跡の追加テストも含む。追跡対象の削除も反映する。`HEAD` や index の内容を代用しない。
- パス、ファイルの内容と実行属性、許可されるシンボリックリンクの参照先から、コピーした内容を識別する。作業ツリーから採取するリンクはリポジトリ内の参照先に限る。隔離コピーはリポジトリ外の `os.tmpdir()` 配下に依頼 ID 別のディレクトリを作り、実パスでもリポジトリ外であることを確認してから、実行ごとに前後を展開する。変更後から採った同一バイト列の追加テストを前後で使う。変更前にもそのパスがあれば新規追加として扱わない。前後は同じランナー、依存関係、許可された資料、実行条件を使う。
- pytest はコピーを `cwd` とし、`--rootdir=<copy>`、`-c <コピー内の設定ファイル、なければ /dev/null>`、`--confcutdir=<copy>`、`-p no:cacheprovider` を指定する。`PYTHONPATH` の先頭にコピーを置き、`src` レイアウトなど公開設定で特定できるコピー内のソースルートも外部の検索パスより前に置く。前後で同じ venv を使い、editable install があってもコピー側の対象コードが優先されることを実行時に確認する。
- `node --test` はコピーを `cwd` にする。Verify が用意する `node_modules` のリンクは、同一のインストール済み依存関係を前後から参照するためのものとし、リンク先は実行プロセスから読み取り専用にする。読み取り専用を保証できない場合は未検証とする。ワークスペースリンクなどで実作業ツリーの対象モジュールに解決された場合は、読み込み元の検査で未検証とする。
- 対象モジュールの読み込み元を必須の実行記録にする。ランナー内で対象の入口を実際に解決・読み込みした際の Python の `module.__file__` または Node の `require.resolve` / `import.meta.resolve` を実パスに正規化し、前後のそれぞれで対応するコピー内にあることを照合する。入口だけが新設された場合は、変更前に入口を提供するはずの既存モジュールの読み込み元と、その入口の不在を記録する。変更前の対象モジュール自体がなく読み込み元を確認できない場合は、入口不在の観測を残して比較は未検証とする。いずれかの側で対象の実パスがコピー外にある場合や、実際の読み込み元を確定できない場合も未検証とする。
- `verify-diff` が、依頼 ID、前後のスナップショット ID、ケース資料の参照、実行件数と結果を実行ごとに追記する。修正前の失敗も残す。有効な証拠は、その依頼で実際に実行した変更後 ID にだけ結び付く。台帳、依頼ごとの状態、ケース JSON、実行記録は作業ツリーの外にある Git 管理領域（`git rev-parse --git-path claude-verify` 配下）に置く。台帳行には ID と要約を置き、依頼の抜粋とケースの詳細は別ファイルに保存する。追記自体は検証した ID を変えない。
- Stop が呼ばれるたびに現在の ID と照合し、ホストが終了を確定した時点では最後の照合結果を使う。検証後に実装か追加テストが変われば、以前の証拠はその最終状態には使えない。追加ターンの枠を使っていれば「未検証」として終了する。

### 2.4 Verify 層の責務

- Verify の手順で参照する範囲は、依頼、対象リポジトリの製品コード・公開テスト・設定、利用者または実行器が明示した資料に限る。テストはその範囲から設計し、許可された資料を使った場合はケースに出典を残す。
- 開始時に公開テスト、共通 fixture、発見・実行設定の保護対象を確定し、`verify-diff` と終了時の証拠照合で開始時点との差分を確認する。検査対象には開始時に存在したパスに加え、新設された共通 fixture と発見・実行設定も含める。テスト関連で新規追加を許すのは、ケースを定義する通常のテストファイルだけとする。既存の保護対象の変更・削除や、共通 fixture と発見・実行設定の新設があれば、有効な証拠を発行しない。発行済みの証拠との照合でも同じ規則を適用する。
- テスト専用パスの既定の保護集合は、公開テストと共通 fixture、サブディレクトリを含む `conftest.py` と `pytest.ini`、テスト設定から参照する Node の `--require`・`--import` の読み込み先を含む。公開設定のテストルートと共有 fixture、およびランナーの既定の探索規則から特定する。対象リポジトリ固有のテスト専用パスは `protectedPaths` で指定できる。
- 多用途ファイルの保護は構文を解析して項目単位で行う。`package.json` は `scripts.test`、`scripts.pretest`、`scripts.posttest`、`pyproject.toml` は pytest 用テーブル（`[tool.pytest]`、`[tool.pytest.ini_options]` とその配下）、`setup.cfg` は `[tool:pytest]`、`tox.ini` は `[pytest]` の追加・変更・削除を検査する。`protectedPaths` でこれらのファイルや親ディレクトリが指定されても、この項目単位の保護を適用する。`bin`、`exports`、製品の依存関係などは依頼に従って変更できる。保護項目を比較できない場合は理由を記録し、未検証とする。
- 評価環境の可視範囲と採点器の隔離は評価リポジトリの責務とする（§4）。Verify の隔離コピーは比較実行用であり、評価用のサンドボックスは外側の実行器が用意する。

### 3.2 モード設定と自動テスト

v0.2 は `verifyV2` を明示したプロファイルに配備する。強制モードはプロファイル専用の `VL_CONFIG_DIR/config.json` に次を設定する。例のランナーとパスは fixture に合わせて選び、既存の設定と併存させる。

```json
{
  "verifyV2": {
    "mode": "enforce",
    "adversarial": false,
    "runner": "node",
    "protectedPaths": ["tests"]
  }
}
```

実行に対応する `runner` は `node` と `pytest`。§4 の評価用生成設定では、対応外を表す `unsupported` も受け取る。その場合は `enforce` のまま Stop の契約を適用し、ランナーを起動せず「未検証（対応外ランナー）」と記録する。Git の除外設定に該当する対象ファイルがある場合は、リポジトリ内のパスを任意設定の `includePaths` に列挙できる。既存テストディレクトリでは §2.4 の規則に従って一意名の通常のテストファイルを新規追加できる。例の `package.json` には §2.4 の項目単位の保護が自動で適用される。導入先の導入先では `observe` で始め、§3.3 の結果を確認した上で `enforce` に切り替える。

`verifyV2` または `verifyV2.mode` を省略した場合、v0.2 のモードは `off` とする。

`node --test tests/verify-v02.test.js` で動作を確認し、リポジトリの既存テストも `node --test` で回す。

- 両ランナーで、後の assertion の実行と合格、および前の期待値不一致、入口不在、収集・依存エラー、前も合格を区別する。0 件、スキップ、assertion に到達しない成功、有効な証拠が得られない場合も確認する。
- 開始時からある編集・未追跡ファイル、未コミットの修正と新しいテスト、依頼中のコミットを含む状態で、比較に使った内容と記録の ID を照合する。台帳追記で証拠が失効せず、検証後に実装だけを直すと失効することを確認する。
- 既存 assertion の弱体化、設定による対象縮小、既存テストの削除、共通 fixture とランナー設定の新設を検出する。許可範囲外を指すリンクやテスト指定は証拠に使えないことを確認する。
- Stop の判定は、対象差分なし、ドキュメントのみ、有効な証拠あり、観察、強制、`stop_hook_active`、同一依頼での再入と次の依頼への切り替えを確認する。最終 ID が変わっても Verify による再ブロックがなく、「未検証」が残ることを確認する。

### 3.3 実セッションでの Stop hook 検証

実装セッションで、Claude Code と Codex のそれぞれに対し、書き捨ての dev fixture を用意する。観測用プロファイルでのみ強制設定を使い、Verify 単独と sample-harness の Stop hook 併用を試す。両方が継続を要求する場合は、設定上の順序を切り替えて観測する。

1. 依頼開始イベントが最初の編集より前に届き、利用者の次の依頼と hook による継続を区別できることを確かめる。ホストのバージョンと、Stop の入力に含まれる `stop_hook_active` の値を記録する。
2. 有効な証拠がない状態で終了させ、Verify の理由がモデルに届くこと、Verify が発生させた追加ターン数、他 hook を含む全体の継続回数を確認する。graph hook だけが先に継続した場合と、両 hook が同じ終了時に継続を求めた場合も確認する。
3. 追加ターンで検証して終了するケースと、検証後に実装を再変更して終了するケースを試す。さらに、同じホストセッションで次の利用者の依頼を送り、介入枠が新しくなることを確かめる。各ケースで最終 ID と台帳の「検証済み」または「未検証」を照合する。
4. 結果をホストと配備構成ごとに保存する。P2 の実配備で依頼開始、理由の配送、依頼ごとの上限、最終記録を確認できたホストだけで P2 を実行する。強制モードを確認できないホストの P2 は「実施不可」と記録し、観察モードで代用しない。導入で併用時の契約を確認できない構成は観察に留め、sample-harness には Verify のケース証拠を渡せるようにする。

## 4. 本評価

- 評価リポジトリは **P0（層なし）、P1（v0.1）、P2（v0.2 単体の強制モード・敵対段 off）** を同じ fixture、依頼、可視範囲、予算で実行する。P2 は §3.4 の同名プロファイルの差し替え方式で配備する。P2 のモードと敵対段 off は事前登録の追補 A で固定済み。Claude と Codex はホスト別に判定し、今回の P0 を比較基準に使う。試行の初期状態と P0 の点検には §3.4 の手順を使う。
- 評価リポジトリの実行器は、全プロファイルと子プロセスが参照できる範囲を、依頼、対象の製品コード、公開テスト、明示した許可資料に制限する。隠しテスト、採点器、他試行の記録は作業環境の外に置く。外側で採点用に加工する前の提出差分を、§2.4 と同じ規則で開始時点と照合する。既存の公開テスト・共通 fixture・発見と実行の設定の変更と削除に加え、共通 fixture や保護対象の設定項目の新設も検出する。テスト関連で新規追加を許すのは通常のテストファイルだけとする。アクセス制限と採点器の保護を評価リポジトリで検証する。
- 評価リポジトリは、全プロファイルで同じ手順により、開始時点との差分で特定した追加テストファイルを除いた新しい採点用コピーを提出物から作る。除外は P2 の命名規則に一致するファイルに限らない。そのコピーに評価用の隠しテストを用意し、隠しテストと元の公開テストのファイルパスを明示して実行する。元の公開テストのパス一覧は開始時点の公開 fixture から確定する。
- 有用性の判定は held-out の結果に基づく。各セル 3 試行とし、P0 の罠の合格率が 20〜80% の範囲外なら判定不能とする。有用の条件は P2 が P0 を上回ること、改善が後退を上回ること、対照の後退が 0、有効試行が 75% 以上であること。漏洩は無効、改ざんは不合格とし、差の信頼区間は副判定に使う。
- 共通の時間・費用の打ち切りは外側の実行器が適用する。ホストと試行の結果を集計する単位、分母、無効・打ち切り・再試行の扱い、予算値は、評価リポジトリの事前登録と追補を正本とする。本実行前に、評価側で架空の結果表を使って「有用」「基準未達」「判定不能」がホスト別に再現されることを確認する。

### 4.1 事前登録の追補 B

評価側は、本実行前に事前登録の追補 B として、P2 の v0.2 単体配備、以下の設定生成と強制モードの可否、上記の全プロファイル共通の採点用コピーとパス指定を固定する。

1. 評価リポジトリが、各 fixture の開始時点の公開ファイル、公開テストと共通 fixture のパス、公開設定だけから P2 の `verifyV2` を機械的に生成する。同じ公開入力には同じ設定を生成し、隠し資材や試行結果による調整を行わない。
2. pytest 設定（`pytest.ini` または §2.4 の pytest 用セクション）があれば `runner: "pytest"` を選ぶ。なければ `package.json` の `scripts.test` が `node --test` の直接呼び出し（引数付きも可）なら `runner: "node"` を選ぶ。どちらにも該当しなければ `runner: "unsupported"` とする。
3. `protectedPaths` には §2.4 の既定集合のうち公開 fixture から特定したテスト専用パスを安定順に出力する。多用途ファイルには §2.4 の項目単位の既定保護を適用し、新設も検査する。`includePaths` は設定しない。`mode: "enforce"` と `adversarial: false` を設定し、生成に使った公開情報と生成結果を評価ログに残す。
4. 対応外ランナーの fixture も P2 を強制モードで実行し、「未検証（対応外ランナー）」を記録する。試行と時間・費用を層の計測に含め、全プロファイル共通の手順で外部採点する。§3.3 の確認が取れなかったホストの P2 は「実施不可」と記録して起動しない。観察モードでの試行による補完は行わない。
