# Verify v0.2 設計 rev6

## 1. ゴール

Verify v0.2 は、Claude Code および Codex がコード変更を終えて応答を返す直前に、既存テストでは見落としやすい「利用者の依頼に対する境界条件の誤り」を、変更前後の隔離環境で公開入口を直接叩く追加テストによって機械的に検出・修正させる検証層である。既存のテスト資産や実行設定を壊さず、1 依頼につき最大 1 回の差し戻しで「期待される振る舞いの変化を実コードの assertion 通過で確認できたか」を監査可能な証拠として残すことで、利用者が手戻りの少ない実装を受け取れる状態を実現する。

### 非ゴール

- 別コンテキストによる敵対的な反例探索（`adversarial: true` は後段。本版では `false` 固定）
- 全言語・全テストフレームワークの汎用サポート（本版は Linux 上の `pytest`・Python 標準 `unittest`・`node --test` の 3 種に限定）
- Windows・macOS 固有の実行環境制御（初期対象は Linux。Mac 配布手順は有用性確認後）
- 2 回以上のループ介入による完全自律修正（コストと暴走の制御上、1 依頼最大 1 介入に制限）
- 評価用セキュリティサンドボックスの提供（隠しテスト隔離と権限境界は評価ハーネスの責務であり、Verify の隔離コピーは前後比較の再現性に特化する）
- 既存テストと依頼が矛盾する場合の自動書き換え（矛盾の報告と保護の維持に留める）

## 2. v0.1 から学んだこと

旧 dev（6 罠・4 対照）での評価 E1b では、Claude 罠で P0 9/12・P1 10/12・P2 9/12、Codex 罠で P1・P2 とも 5/6 となり、v0.1 は実用上の改善をもたらさなかった。因果は次の 3 点にある。

1. **到達の欠如**: Claude P2 で verify スキルが呼ばれたのは 4/12 に留まり、コミット後 hook は観察記録だけで終了を止められなかった。エージェントは既存テスト通過時点で早合点して終了した。
2. **検証契約の不在**: Codex P2 では全 6 試行で `mark verify` が実行されたが成績は伸びなかった。「テストを回した」という手続き完了だけで通過でき、依頼固有の境界入力を選んで変更前後の差を assertion で確認する要件がなかったためである。
3. **ベースライン汚染**: 旧 P0 は fixture 内の verify スキルを参照でき、層なし比較として不完全だった。

よって v0.2 は、(a) 終了時の強制差し戻し、(b) 境界選定と前後 assertion 通過の証拠契約、(c) 汚染を排除した held-out 比較、の 3 点を一体で設計する。

|---|---|---|---|

## 4. 仕様（最小版）

### 4.1 終了時の介入（Stop 契約）

- **対象依頼**: 依頼開始時から終了時までに、ドキュメント以外のコード・設定に差分が生じた依頼（コミット有無は不問）。
- **依頼 ID**: 依頼開始 hook でセッション間に衝突しない ID を発行する。ファイル名と Python モジュール名にそのまま使えるよう、文字種は `^[a-z][a-z0-9_]{7,31}$`（例: `req_a1b2c3d4e5f6`）に限定する。Stop hook の継続中は同一 ID を維持し、次のユーザー依頼で更新する。依頼開始イベントを取得できないホストでは `enforce` の前提を満たさないため、評価では「実施不可」とする（観察で代用しない）。
- **介入回数と再入防止**: `enforce` モードで未検証の場合、ブロックによる追加ターン発生は **1 依頼 ID につき最大 1 回**とする。ブロックを返す直前に台帳へ「介入済み」を記録する。`stop_hook_active` が真のとき、または当該依頼 ID が介入済みのときは、他 hook 継続後も含めて再ブロックしない。Stop の理由文には「実装が誤っている可能性が最も高い境界入力を探し、公開入口で前後比較する」旨と §4.2 の最小手順、判明している失敗理由を記載する。
- **モードと対応外ランナー**:
  - `off`（`verifyV2` または `mode` 省略時の既定）: 無効。
  - `observe`: 判定と記録のみ行いブロックしない。
  - `enforce`: 未検証時に 1 回のみブロック。ただし `runner: "unsupported"` の場合はランナーを起動せず、Stop hook 発火と **`未検証（対応外ランナー）`** を台帳に記録し、**ブロックせず（追加ターンを発生させず）終了を許可する**。
  - hook 内部エラー時は fail-open（ブロックせず、可能なら `未検証（hook 失敗）` を記録）。
- **意図した変更（仕様矛盾）**: 依頼を満たすために既存テストの期待値と矛盾が生じる場合、既存テストを変更せず依頼された実装と既存テストの両方を維持し、依頼の該当箇所と失敗テスト識別子・矛盾内容を報告して終了する。最終 Stop はこれを **`未検証（意図した変更）`** として通常の `未検証` と別区分で記録・集計する。保護検査と証拠規則は引き続き適用する。

### 4.2 証拠の契約

Verify が発行する「検証済み」は、**最終スナップショット ID において以下の全条件を満たすこと**を機械的に証明した状態とする。

1. **境界候補の選定（ケース JSON）**:
   - ケース JSON ごとに境界候補を **3〜5 件**列挙する（候補 ID、依頼の該当箇所、具体入力、境界種別［サイズ・空/端値・表記・順序・失敗応答等］、現実装に明示処理があるか）。バグ報告に再現条件があれば第 1 候補にする。
   - 依頼または許可資料から期待値が一意に定まり、現実装が最も誤りやすい 1 件を選び、選定理由・公開入口と呼び出し方・入力・期待値・テストファイル相対パス・テスト識別子・指定 assertion の位置・対象モジュール名を記す。
   - 依頼文の例または既存公開テストと同じ入力には `nonBoundary: true` を付ける（実行器でも具体値照合できる範囲で自動付与）。`nonBoundary` ケースは記録を残すが「境界の証拠」から除外する。
2. **ケース上限と未解消失敗の追跡**:
   - `vl.js verify-diff --case <JSON>` は **1 依頼 ID あたり異なる `caseId` を最大 3 件まで**受け付ける（コマンド分割をまたいで合算し 4 件目を拒否）。同じ `caseId` の再実行（実装修正後の再検証）は新規件数に加算しない。
   - 当該依頼 ID で一度でも変更後 assertion 失敗または実行エラーを出した `caseId` は、台帳の未解消集合（`openFailures`）に登録する。最終判定で「検証済み」とするには、**`openFailures` 内の全 `caseId` が最終スナップショット ID で合格していること**を必須とする（失敗したケース B を無視してケース A だけ再実行する抜け道を塞ぐ）。
   - 最終スナップショットで、少なくとも 1 件の有効な境界ケース（`nonBoundary: false` かつ前後条件充足）が合格していること。
3. **追加テストファイルの規約**:
   - `verify-diff` で前後注入する追加ケースは、依頼 ID を含む一意名の新規ファイルに標準テスト記法で書く（Python: `test_vl_<request_id>_<slug>.py`、Node: `<slug>.vl_<request_id>.test.js` または `.mjs`）。変更前スナップショットに同名パスが存在する場合は拒否する。Verify 専用ヘルパーを import せず、通常ランナーでも実行可能とする。
4. **変更前結果の 4 分類**:

| 変更前の結果 | 証拠としての扱い |
|---|---|
| **期待値不一致**（指定 assertion で失敗） | 変更後の同 assertion 合格と合わせ、有効な境界証拠とする |
| **公開入口なし**（既存モジュールの属性・シンボル不在、または**新規モジュール不在**） | 入口追加を求める依頼に限り変更後合格と合わせて有効とする（バグ再現とは別集計）。新規モジュール不在は、(a) 対象モジュール名を指す `ModuleNotFoundError` / `ERR_MODULE_NOT_FOUND` が発生し、(b) 探索起点（Python の `sys.path[0]` および親パッケージの `__file__`、Node の解決起点パス）が変更前コピー内にあることを記録できた場合のみ認定する |
| **実行・環境エラー**（上記以外の import・構文・依存・起動失敗、読み込み元がコピー外） | 未検証 |
| **期待値に一致** | 変更後動作の観測記録のみ。変更による差分の証拠にはしない（未検証） |

5. **既存公開テストの前後比較と同一条件再実行**:
   - 依頼開始時（前）と検証時（後）の隔離コピーで、既存の公開テスト一式を同一条件・同一順序で実行し、テスト識別子ごとの合否を記録する。
   - 開始時に合格したテストが変更後に失敗した場合、**単独再実行は行わない**。残り予算内で新しい変更後隔離コピーを作り、**初回と同一のテスト集合・同一順序でスイート全体を 1 回だけ再実行**する。2 回目も失敗なら「新規回帰（未検証）」、2 回目で合格すれば「不安定（両回結果を記録し新規回帰に数えない）」。
   - 収集エラー、ランナー異常終了、予算不足による再実行未完、開始時合格テストの個別結果が 1 件でも照合不能な場合は、理由を記録して「未検証」とする。

### 4.3 3 ランナーの隔離実行と assertion 到達計測

全ランナー共通で、**対象モジュールの読み込み元実パス（Python `os.path.realpath(module.__file__)` / Node `fs.realpathSync(resolve(...))`）が前後それぞれ対応する隔離コピー内にあること**を必須記録とする（新規モジュール不在時は §4.2-4 による探索起点のコピー内記録）。また 0 件・収集のみ・skip・todo・xfail・途中終了・assertion 未到達はいずれも未検証とする。

| ランナー | 隔離起動と探索固定 | assertion 到達の動的記録 | 静的検査（AST）と抜け道対策 |
|---|---|---|---|
| **`pytest`** | 新しい `__pycache__` のないコピーを `cwd`、`--rootdir=<copy>`、`-c <コピー内設定または/dev/null>`、`--confcutdir=<copy>`、`-p no:cacheprovider`、`PYTHONPATH` 先頭にコピー（および公開 `src` ルート）。コピー外プラグインを `-p` で読み込み、`-o enable_assertion_pass_hook=true` を付与 | 外部プラグインが `pytest_assertion_pass` をテスト識別子と位置ごとに記録し、`call` フェーズ成功と照合。変更前の不一致は指定位置の `AssertionError` を `call` 結果から確認（入口不在は `collect`/`call` 両方で捕捉） | Python AST で指定 `assert` 文が `AssertionError`/`Exception`/`BaseException`/bare `except` に囲まれて握りつぶされていないこと、`pytest.skip`/`xfail` 不在を検査 |
| **`unittest`** | コピーを `cwd`、`python -B`（`PYTHONDONTWRITEBYTECODE=1`）、`PYTHONPATH` 先頭にコピー（および公開 `src` ルート）。コピー外ラッパー `vl_unittest_runner.py` が **発見実行**（`TestLoader.discover` 相当＋`test.id()` 辞書順で安定ソート）と **明示パス実行**（対象モジュール／ファイル／テスト識別子指定）の両方を担う | ラッパーがテストロード直前に `unittest.TestCase` の全 `assert*` メソッドおよび `fail` をラップする。通常メソッドは例外なく返却した時点で `(test.id(), メソッド名, ファイル, 行番号, subTest深さ)` を通過記録。**`assertRaises` / `assertRaisesRegex` / `assertWarns*` / `assertLogs*` のコンテキストマネージャ版は `__exit__` が検証成功で抜けた時点のみ通過記録**する。失敗時は失敗位置を記録し再送出。カスタム `TestResult` の `addSuccess` と通過記録を 1 対 1 照合（入口不在はロード・実行両フェーズで捕捉） | **(1) `try/except` 握りつぶし**: AST で指定 `self.assert*` が例外捕捉ブロック内にないことを強制し、動的記録に `assertion_failed` が 1 件でもあれば `addSuccess` でも拒否。<br>**(2) `self.assert*` 以外の比較**: 追加ケースの指定比較を `self.assert*` 直接呼び出しに限定し、素の `assert` や `if/raise` のみのテストを AST で拒否。<br>**(3) `subTest` の抜け道**: `addSubTest` をフックし `err is not None` が 1 件でもあれば失敗扱い。さらに指定 `self.assert*` の動的通過回数 >= 1 を必須とし、空ループによる 0 回成功を排除。<br>**(4) skip・改ざん**: `addSkip`/`addExpectedFailure`/`addUnexpectedSuccess` は未検証。`TestCase` や `self.assert*` への代入・モンキーパッチを AST で拒否 |
| **`node`** | コピーを `cwd` とし、`node --test --test-reporter=<コピー外reporter> <明示パス>`。元ツリーに `node_modules` がある場合は、コピー内に独立複製（`cp -a --reflink=auto`、上限 512MB）してコピー側のみ `chmod -R a-w` で読み取り専用化し、対象パッケージへのワークスペースリンクをコピー内へ張替える（削除時は `chmod -R u+w`）。上限超過等で隔離できない場合は未検証 | 追加テスト先頭で `t.plan(1)` を宣言し、比較に `t.assert.*` を使用。コピー外 reporter がテスト識別子ごとの成功・比較失敗・plan 未達・skip・todo・途中終了を記録し照合 | JavaScript AST 静的検査で以下を強制：(1) コールバック本体トップレベルに `t.plan(1)` が 1 回ある、(2) `t.assert.*` 呼び出しがテスト本体全体で指定位置の **1 か所のみ**（指定外比較での plan 充足を禁止）、(3) その呼び出しが `try`/`.catch`/条件分岐/ループ/別コールバックの内側にない（`try { t.assert... } catch {}` 握りつぶしを禁止）、(4) `skip`/`todo` 指定がない |

### 4.4 前後のスナップショットと台帳

- **変更前**: 依頼開始 hook 時点で、作業ツリー（ステージ済み・未ステージ変更、`.gitignore` 対象外の未追跡ファイル、および任意の `includePaths`）の内容・実行属性・リポジトリ内参照に限ったシンボリックリンク先からスナップショット ID を算出し固定する。作業ツリーや Git index を改変せず、依頼途中のコミットでも基準を更新しない。
- **変更後**: `verify-diff` 実行時および Stop 照合時に同一規則で採取する（未コミット変更・未追跡ファイル・削除を反映）。
- **隔離コピー**: リポジトリ外の `os.tmpdir()` 配下に依頼 ID 別の作業領域を作り、`realpath` がリポジトリ外であることを確認して毎回前後を展開する。変更後から採取した同一バイト列の追加テストを前後双方に配置する。
- **台帳**: 状態・ケース JSON・実行記録は作業ツリー外の Git 管理領域（`git rev-parse --git-path claude-verify` 配下）に保存し、追記自体はスナップショット ID を変えない。検証後に実装または追加テストが変化すれば、最終 Stop 時の ID 照合で旧証拠は自動的に失効し、介入済みなら「未検証（検証後の変更）」で終了する。

### 4.5 保護対象と意味単位（AST）の差分検査

文字列・行単位の差分禁止は正当なテスト追加を誤検出するため（資料 F の教訓）、Verify の保護検査と評価側の改ざん検査は**共通の意味単位（AST・構造解析）規則**を採用する。違反があれば有効な証拠を発行せず、既存証拠も照合不可とする。

- **既存テストファイル（AST 意味判定）**:
  - **許可**: 通常テストファイルの新規作成、および既存テストファイルへの**純粋な追加**（新しいテスト関数／テストメソッドの追加、補助関数の追加、既存 `import` 文への新規シンボル追記、それに付随する新規定数定義）。
  - **禁止**: 開始時に存在したテストファイル・テストクラス・テスト関数／メソッドの削除・リネーム、既存テスト本体の AST 改変（assertion の削除・弱体化・条件回避・例外握りつぶし等）、既存テストへのデコレータ（`skip`/`xfail` 等）追加・変更・削除、既存テストが参照する `setUp`/`tearDown`/fixture/モジュール変数等の既存束縛の変更・削除。
- **テスト専用インフラ**: 開始時に存在する共通 fixture、`conftest.py`、`pytest.ini`、Node の `--require`/`--import` 読み込み先、および `protectedPaths` 指定パスの変更・削除に加え、**共通 fixture とテスト発見・実行設定ファイルの新設**を禁止する。
- **多用途ファイルの項目単位＋推移閉包保護**:
  - Python: `pyproject.toml`（`[tool.pytest]` 配下）、`setup.cfg`（`[tool:pytest]`）、`tox.ini`（`[pytest]`）の追加・変更・削除を構造解析で禁止。製品メタデータ・依存関係は変更可。

## 6. 決定的な評価の計画（事前登録に入れる追補 B の文面案）

本節は、既存の事前登録本体（PREREG: 2026-11-19）、追補 A（2026-11-20）、追補 B-0（2026-11-23 較正手順）を**一切変更せず**、held-out の本評価結果を見る前（P2 試行 0 件の時点）に新たに固定する **追補 B** の文面案である。

### 6.1 評価対象・盲検性・較正との関係

- 有用性の判定は **held-out セット（罠 6 件以上 + 対照 3 件以上）のみ**で行い、旧 dev 6 罠（`tasks-e1b`）は判定に含めない。
- 本設計（rev6）の著者は held-out の罠の個別内容・再現条件・隠しテストを閲覧しておらず、今後も閲覧しない。`unittest` ランナー対応は、結果を見ない段階で判明した公開 OSS テスト基盤の汎用要件に対する拡張であり、個別の罠に合わせた特化設計は行わない。
- ホスト別（Claude / Codex）の本番評価で、P0 の罠合格率が **20〜80% の範囲外**となった場合は再較正せず、PREREG 通りに **`判定不能（INCONCLUSIVE）`** とする。事前の難易度較正は追補 B-0（Claude P0・6 罠 × 2 試行・合算値のみ・最大 2 回・本番非混入・別計上）に従う。

### 6.2 不正防止・AST 改ざん判定・全プロファイル共通の外部採点

- **隔離と漏洩検査**: 隠しテスト、採点器、他試行ログは solver および子プロセスから到達不能な作業環境外に配置する。canary を含む `leak_check` を全試行で自動実行し、漏洩検出時は **`INVALID`**（合否分母から除外し有効率 75% 判定に算入、再試行なし）とする。
- **AST 意味単位の改ざん判定（資料 F の反映）**: 行単位判定が「既存 unittest クラスへの新テストメソッド挿入」「既存 `import` 文への名前追記」を改ざん誤判定して P0 を見かけ 16.7% の床にした教訓を踏まえ、評価側の `tamper_check` と Verify の保護判定（§4.5）に**同一の AST 意味判定規則**を適用する。既存テスト本体の改変・削除・デコレータ変更・間接テスト設定を含む設定改変・共通 fixture 新設のみを改ざん（不合格）とし、純粋な追加は許容する。較正開始前に、資料 F の実データ 6 罠で **偽陽性 0 件**、合成改ざんセットで **検出率 100%** を確認・記録してから固定する。
- **共通採点コピー**: 全プロファイル（P0 / P1 / P2）に対し同一手順で提出物から採点用コピーを作る。開始時差分で特定した新規追加テストファイル（命名規則を問わない）をすべて除外し、既存公開テストファイルは開始時点のオリジナル版に復元した上で、元の公開テストと隠しテストを明示パスで実行する。主判定は決定的な隠しテストのみとし、副次 LLM 判定（別系統・盲検）は参考値に留める。

### 6.3 P2 の配備・`verifyV2` 機械的生成規則・`unsupported` の挙動

- **P2 単体配備**: P2 は既存プロファイル（Claude `claude-verify-layer` / Codex `codex-verify-layer`）を v0.2 単体（`mode: "enforce"`, `adversarial: false`）へ差し替え、v0.1 資材は P1 に限定する。起動前に `.git/claude-verify` の不在・空、および P0 への Verify 要素・共通ルール汚染がないことを自動点検する。
- **`verifyV2` 機械的生成規則**: 評価ハーネスが各 fixture の開始時点の公開ファイル・公開設定・公開テスト実行環境のみから決定論的に生成し、入力と生成結果をログに保存する（隠し資材や試行結果による調整を禁止）。優先順位は次の通り。
  1. 公開設定（`pytest.ini`、`pyproject.toml` の `[tool.pytest*]`、`setup.cfg` の `[tool:pytest]`、`tox.ini` の `[pytest]`、`conftest.py`）があるか、公開依存に `pytest` が明示され Python テストファイル（`test*.py` / `*_test.py`）があり、かつ実行環境に `pytest` が存在する → `runner: "pytest"`。
  2. (1) に該当せず、Python テストファイルが存在し、その 1 件以上が AST 上 `unittest` 参照または `TestCase` 継承を含む → `runner: "unittest"`（公開テスト配置から `unittestStartDir` と `unittestPattern` を機械的に確定）。
  3. (1)(2) に該当せず、Python テストファイルにトップレベル `def test_*` 関数が存在し、実行環境に `pytest` が存在する → `runner: "pytest"`。
  4. (1)〜(3) に該当せず、`package.json` の `scripts.test`（推移閉包含む）が `node --test` を直接呼ぶ → `runner: "node"`。
  5. いずれにも該当しない → `runner: "unsupported"`。
- `protectedPaths` は公開 fixture から特定したテスト専用パスを安定ソートで出力し、多用途ファイルには §4.5 の項目単位＋推移閉包保護を自動適用する。`includePaths` は未設定とする。
- **`unsupported` 時の Stop 挙動**: Stop hook は発火して台帳に `未検証（対応外ランナー）` を記録し、**ブロックせず（追加ターンを発生させず）終了を許可する**。試行と時間・費用は層の計測に含め、共通手順で外部採点する。実セッション検証で強制モードを確認できないホストの P2 は「実施不可」として起動せず、観察モードで代用しない。
- **診断集計**: `未検証（意図した変更）`、`未検証（対応外ランナー）`、通常 `未検証` を分離集計する。held-out 公開後、誤りが残った試行を「選び方の失敗」「検出の失敗」「修正未完」「ケース未選定」「記録欠落」に分類記録する。

## 8. リスクと未決事項

1. **境界選定の質（選び方の失敗）**: 候補列挙と選定理由を強制しても、モデルが実装の真の誤り箇所ではなく無関係な境界を選べばバグを逃す。同一コンテキスト 1 ターン介入の限界であり、本評価で「選び方の失敗」が支配的なら次段で敵対段（fresh-context）を別事前登録で検討する。
2. **AST 検査の記述制約と構文カバレッジ**: `unittest` で独自ヘルパー関数越しに `self.assert*` を呼ぶ記法や素の `assert` は規約外として弾くため、SKILL と Stop 理由での明確な案内が不可欠。また JS 側 AST 解析は追加依存を抑えつつ ESM/CommonJS を確実に扱えるパーサ実装を作業 2 の冒頭で確定する必要がある。
3. **スイート全体再実行の予算圧迫**: 順序依存回帰の見逃しを防ぐため単独再実行を廃止した結果、実行時間の長い既存スイートで不安定テストが出ると、再実行だけで共通 `timeout_s` を圧迫し「予算不足による未検証」が増えるおそれがある。
4. **`node_modules` 独立コピーの上限（512MB）**: 大規模 Node リポジトリでは隔離上限超過で未検証になり得る。rootless な OverlayFS 等による軽量 RO 隔離は将来の拡張課題とする。
5. **ホスト CLI の Stop hook 互換性**: Claude Code・Codex のアップデートや sample-harness 併用時の `stop_hook_active` 挙動は作業 5 の実セッション検証まで確定しない。片側ホストが「実施不可」となるリスクが残る。
6. **「未検証（意図した変更）」の過大申告**: モデルが自分の誤りによる既存テスト失敗を意図した変更と申告して終了する可能性がある。評価の合否は外部隠しテストで決まるため実験は歪まないが、実運用時は別集計比率を監視する必要がある。
7. **定額プラン枠による評価期間の延伸**: 5h 45%・7d 88% の停止規則により、全 162 試行と副次判定の完了に複数日〜週単位を要し、途中でホスト CLI やモデル更新が混入するリスクがある。各チャンクでバージョンを記録し、変更があれば評価ログに明示する。
