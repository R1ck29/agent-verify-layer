# Verify v0.2 設計 rev12

## 1. ゴール

Verify v0.2 は、Claude Code および Codex がコード変更を終えて応答を返す直前に、既存テストでは見落としやすい「利用者の依頼に対する境界条件の誤り」を、変更前後の隔離環境で公開入口を直接叩く追加テストによって機械的に検出・修正させる検証層である。既存のテスト資産や実行設定を壊さず、1 依頼につき最大 1 回の差し戻しで「期待される振る舞いの変化を実コードの assertion 通過で確認できたか」を監査可能な証拠として残すことで、利用者が手戻りの少ない実装を受け取れる状態を実現する。

### 非ゴール

- 別コンテキストによる敵対的な反例探索（`adversarial: true` は後段。本版では `false` 固定）
- 全言語・全テストフレームワークの汎用サポート（本版は Linux 上の `pytest`・Python 標準 `unittest`・`node --test` の 3 種に限定）
- Windows・macOS 固有の実行環境制御（初期対象は Linux。Mac 配布手順は有用性確認後）
- 2 回以上のループ介入による完全自律修正（コストと暴走の制御上、1 依頼最大 1 介入に制限）
- 評価用セキュリティサンドボックスの提供（隠しテスト隔離と権限境界は評価ハーネスの責務であり、Verify の隔離コピーは前後比較の再現性に特化する）
- 既存テストと依頼が矛盾する場合の自動書き換え（矛盾の報告と保護の維持に留める）

## 2. v0.1 から学んだこと

旧の開発用評価（罠 6 件・対照 4 件）では、層を付けた条件でも層なしと比べて実用上の改善は見られなかった。因果は次の 3 点にある。

1. **到達の欠如**: 一方のホストでは、層あり条件でも verify スキルが呼ばれることが少なく、コミット後 hook は観察記録だけで終了を止められなかった。エージェントは既存テスト通過時点で早合点して終了した。
2. **検証契約の不在**: もう一方のホストでは、ほぼすべての試行で検証手続きが実行されたが成績は伸びなかった。「テストを回した」という手続き完了だけで通過でき、依頼固有の境界入力を選んで変更前後の差を assertion で確認する要件がなかったためである。
3. **ベースライン汚染**: 旧 P0 は fixture 内の verify スキルを参照でき、層なし比較として不完全だった。

よって v0.2 は、(a) 終了時の強制差し戻し、(b) 境界選定と前後 assertion 通過の証拠契約、(c) 汚染を排除した held-out 比較、の 3 点を一体で設計する。

## 4. 仕様（最小版）

### 4.1 終了時の介入（Stop 契約）

- **対象依頼**: 依頼開始時から終了時までに、ドキュメント以外のコード・設定に差分が生じた依頼（コミット有無は不問）。
- **依頼 ID と依頼文**: 依頼開始 hook でセッション間に衝突しない ID を発行する。ファイル名と Python モジュール名にそのまま使えるよう、文字種は `^[a-z][a-z0-9_]{7,31}$`（例: `req_a1b2c3d4e5f6`）に限定する。Stop hook の継続中は同一 ID を維持し、次のユーザー依頼で更新する。依頼開始 hook は依頼文を台帳に保存する（§4.2-4 の字句照合に使う）。依頼開始イベントを取得できないホストでは `enforce` の前提を満たさないため、評価では「実施不可」とする（観察で代用しない）。依頼文を取得できないホストでは「公開入口なし」の証拠を常に未検証とする。
- **介入回数と再入防止**: `enforce` モードで未検証の場合、ブロックによる追加ターン発生は **1 依頼 ID につき最大 1 回**とする。ブロックを返す直前に台帳へ「介入済み」を記録する。`stop_hook_active` が真のとき、または当該依頼 ID が介入済みのときは、他 hook 継続後も含めて再ブロックしない。Stop の理由文には「実装が誤っている可能性が最も高い境界入力を探し、公開入口で前後比較する」旨と §4.2 の最小手順（指定 assertion の形、ケース JSON の型付き入力と `inputFiles` の列挙、ケースの固定と取り下げを含む）、判明している失敗理由を記載する。
- **モードと対応外ランナー**:
  - `off`（`verifyV2` または `mode` 省略時の既定）: 無効。
  - `observe`: 判定と記録のみ行いブロックしない。
  - `enforce`: 未検証時に 1 回のみブロック。ただし `runner: "unsupported"` の場合はランナーを起動せず、Stop hook 発火と **`未検証（対応外ランナー）`** を台帳に記録し、**ブロックせず（追加ターンを発生させず）終了を許可する**。
  - 取り下げ（§4.2-2）がある依頼は「検証済み」に到達できないため、Stop はブロックせず **`未検証（ケース取り下げ）`** を記録して終了を許可する。取り下げ理由は利用者への報告に含める（SKILL で案内する）。
  - hook 内部エラー時は fail-open（ブロックせず、可能なら `未検証（hook 失敗）` を記録）。
- **意図した変更（仕様矛盾）**: 依頼を満たすために既存テストの期待値と矛盾が生じる場合、既存テストを変更せず依頼された実装と既存テストの両方を維持し、依頼の該当箇所と失敗テスト識別子・矛盾内容を報告して終了する。最終 Stop はこれを **`未検証（意図した変更）`** として通常の `未検証` と別区分で記録・集計する。保護検査と証拠規則は引き続き適用する。

### 4.2 証拠の契約

Verify が発行する「検証済み」は、**最終スナップショット ID において以下の全条件を満たすこと**を機械的に証明した状態とする。

1. **境界候補の選定（ケース JSON）**:
   - ケース JSON ごとに境界候補を **3〜5 件**列挙する（候補 ID、依頼の該当箇所、具体入力、境界種別［サイズ・空/端値・表記・順序・失敗応答等］、現実装に明示処理があるか）。バグ報告に再現条件があれば第 1 候補にする。
   - 依頼または許可資料から期待値が一意に定まり、現実装が最も誤りやすい 1 件を選び、選定理由・公開入口（対象モジュール名とシンボル名）と呼び出し方・入力・期待値（例外を期待する場合は例外の型名）・テストファイル相対パス・テスト識別子・指定 assertion の位置を記す。変更前に入口が存在しない（入口を追加する）ケースでは、追加を求める依頼の 1 文を `entryAdditionQuote` に引用する（§4.2-4）。
   - **入力は型付きで書く**: 選んだケースの `input` は、入口に渡す位置引数の並び `args` とキーワード引数の並び `kwargs`（`[引数名, 型付き値]` の組の配列。Node は空配列）を、§4.2-3「入口の実引数の照合」と同じ型付きの正規化 JSON（各値を `{"type": 型名, "value": 値}` で表す。辞書・オブジェクトの `value` は順序を保つ `[キー, 型付き値]` の組の配列とする。例: 空文字は `{"type": "str", "value": ""}`、整数の 1 は `{"type": "int", "value": 1}`、真は `{"type": "bool", "value": true}`、辞書は `{"type": "dict", "value": [["b", {"type": "int", "value": 1}], ["a", {"type": "int", "value": 2}]]}`）で書く。実行器はこれを実引数と照合し、可変コンテナの参照共有、Python の組み込み型サブクラス、または Node の凍結・拡張不可・書き込み不可等の通常 JSON 以外の属性を持つオブジェクト／配列がある実行は未検証にする（§4.2-3）。
   - **`inputFiles`**: 入口または入力の準備が読むデータファイルのうち、変更前スナップショットに存在しない新規ファイル、または変更前から存在する保護対象外のファイルで変更後の内容を前後双方へ同一配置したいものは、コピー内の相対パスを `inputFiles` に列挙する（変更前から存在し内容・権限が変わらないファイルは列挙不要で、§4.2-3 により自動で前後一致と登録時固定の対象になる。該当がなければ空配列）。列挙できるのは、コードとして読み込まれない非保護ファイルだけとする（Python・JS のソース、`__init__.py`、`conftest.py`、`package.json`、§4.5 のテスト設定・多用途ファイル・保護対象ファイルは列挙できず、列挙すれば `verify-diff` は拒否する）。扱いは §4.2-3「入力に使うデータファイルとコピー内ファイルの参照」による。
   - 依頼文の例または既存公開テストと同じ入力には `nonBoundary: true` を付ける。実行器は、記録した実引数の直列化値（§4.2-3）を、依頼文から取り出せるリテラルと、既存公開テストで入口に渡されたリテラルに照合して自動付与する。判定には実引数を使い、ケース JSON に書いた `nonBoundary: false` より照合の結果を優先する。`nonBoundary` ケースは記録を残すが「境界の証拠」から除外する。
2. **ケース上限・ケースの固定・未解消失敗の追跡**:
   - `vl.js verify-diff --case <JSON>` は **1 依頼 ID あたり異なる `caseId` を最大 3 件まで**受け付ける（コマンド分割をまたいで合算し 4 件目を拒否）。同じ `caseId` の再実行は件数に加算しない（固定後に内容を変える場合は下記）。
   - **未解消失敗への登録**: 変更後の実行で、公開入口が呼ばれた（§4.3 の条件 C）うえで指定 assertion の比較が失敗した、または指定呼び出しが期待と異なる例外で抜けた（送出時の呼び出し履歴が入口のフレームを通るものに限る。§4.2-3 の「例外の出所」）`caseId` を、台帳の未解消集合（`openFailures`）に登録する。公開入口に到達する前の失敗（追加テストの構文誤り・収集失敗・対象モジュールの読み込み失敗・入口の不在）、入口のフレームを通らない例外、実引数がケース JSON の入力と一致しない（辞書・オブジェクト・`kwargs` の順序違いを含む）・直列化できない・Python の組み込み型サブクラスまたは Node の凍結・書き込み不可等の通常 JSON 外属性を持つ・可変コンテナの参照共有がある場合（§4.2-3「入口の実引数の照合」）、`inputFiles` に列挙していない新規ファイルや前後で状態（権限ビット・確認した権限・該当時のディレクトリ項目一覧を含む）が異なるコピー内パスを参照・存在確認・削除等のパス操作の対象にした場合（§4.2-3「入力に使うデータファイルとコピー内ファイルの参照」）、入口内で起動した子プロセスの参照記録を取得できなかった場合（§4.2-3「プロセス起動と子プロセスのファイル参照」）は登録せず「実行エラー」として返し、同じ `caseId` のまま直して再実行できる。
   - **登録時の固定**: 登録と同時に、固定項目（入力・`inputFiles` の一覧・期待値・公開入口と呼び出し方・対象モジュール名・テストファイル相対パス・テスト識別子・指定 assertion の位置）を配列順序を保って正規化した JSON の SHA-256、追加テストファイルのバイト列の SHA-256、`inputFiles` の各ファイルのバイト列の SHA-256 と権限ビット（`st_mode & 0o777`）、および追加テストの実行中（入口の内側・外側および入口内で起動した子孫プロセスを含む）に参照・存在確認・権限確認・一覧取得および削除・作成・変更等のパス操作を行った全コピー内パスのスナップショット初期状態（§4.2-3。権限ビット・確認した権限および該当時のディレクトリ項目一覧を含む）を台帳に固定する。入口の実引数は、各実行でケース JSON の入力との一致（辞書・オブジェクト・`kwargs` の順序を含む）と可変コンテナの参照非共有、Python 厳密型・Node の通常 JSON 属性を要するため、入力の固定によって固定される。以後の変更後実行と最終実行で、実引数がケース JSON の入力と一致しない・可変コンテナの参照共有または Node の凍結・書き込み不可等の通常 JSON 外属性がある場合、入口内で起動した子プロセスの参照記録を取得できなかった場合、または `inputFiles` や固定したコピー内パスのスナップショット初期状態が固定値と異なる場合（変更前から存在する非保護ファイルの書き換え・権限変更・削除、または不在だったファイルの新設を含む）は、そのケースを合格に数えず `openFailures` に残す。選定理由と候補一覧の文面は固定しない。固定後に同じ `caseId` で内容の違うケースまたは追加テストを渡すと `verify-diff` は拒否し、「内容を変えるなら新しい `caseId` を使う（残り n 件）。元のケースは未解消のまま残る」と返す。内容を変えたケースは新しい `caseId` として上限に数え、元のケースは `openFailures` に残る。
   - **取り下げ**: 期待値の誤りに気づいたときは `vl.js verify-diff --withdraw <caseId> --reason "<理由>"` で、`openFailures` 内のケースを理由付きで取り下げる。取り下げは台帳に残り、取り消せない。取り下げがある依頼の最終判定は `未検証（ケース取り下げ）` とする。
   - **最終判定**: 「検証済み」には次の全てを要する。(a) 取り下げが 0 件。(b) `openFailures` 内の全 `caseId` が、固定した内容のまま最終スナップショット ID で合格。(c) 少なくとも 1 件の有効な境界ケース（`nonBoundary: false` かつ §4.2-4 の前後条件充足）が最終スナップショット ID で合格。
3. **追加テストファイルと指定 assertion の形**:
   - `verify-diff` で前後注入する追加ケースは、依頼 ID を含む一意名の新規ファイルに標準テスト記法で書く（Python: `test_vl_<request_id>_<slug>.py`、Node: `<slug>.vl_<request_id>.test.js` または `.mjs`）。1 ファイルに 1 ケース・1 テストだけを書く。変更前スナップショットに同名パスが存在する場合は拒否する。Verify 専用ヘルパーを import せず、通常ランナーでも実行可能とする。
   - **比較は 1 文だけ、テスト本体の直下で 1 回だけ**: 指定テスト（関数・メソッド・`test()` の本体）の中の assertion は指定の 1 文だけとする（pytest の `assert` 文と `pytest.raises`、unittest の `self.assert*` と `self.fail`、Node の `t.assert.*` を数える）。指定 assertion の行に他の文を置かない。指定 assertion はテスト本体の直下の文とし、ループ・条件分岐・`try`・`with`（例外を期待する形の `with` 自体を除く。`contextlib.suppress` を含む）・入れ子の関数の内側に置かない。実行時には、指定 assertion の通過または失敗の記録がちょうど 1 件であることを要する（0 件・2 件以上は未検証）。指定テストには `pytest.mark.asyncio`・`pytest.mark.anyio` 以外のデコレータを付けない。
   - **実測側は公開入口の直接呼び出し**: 指定 assertion の実測側は公開入口の直接呼び出し 1 つ（`await` 付きを含む）とする。呼び出し先は、import で束縛した入口名、または import で束縛した名前から属性をたどった名前（例: `Parser.parse`）に限り、準備した値のメソッド呼び出し（`p.parse(...)`）は使わない。引数は名前とリテラル（リテラルだけを要素に持つ組・リスト・辞書・オブジェクトを含む）に限り、`*`・`**`・スプレッドによる展開は使わない。入力の準備は指定 assertion より前の別の文で行う。公開入口の名前を追加テスト内で再束縛しない。
   - **期待値側はリテラル**: 値を期待する比較は、等値（pytest `assert 実測 == 期待値`、unittest `self.assertEqual(実測, 期待値)`、Node `t.assert.strictEqual`／`deepStrictEqual(実測, 期待値)`）と、`None`／真偽との同一性（pytest `assert 実測 is None|True|False`、unittest `self.assertIs(実測, None|True|False)`・`self.assertIsNone(実測)`。期待値はそれぞれ `None`・`True`・`False` としてケース JSON と照合する）に限る。期待値側は、リテラル（数値・文字列・真偽・`None`／`null`、負号付きの数、それらだけを要素に持つ組・リスト・辞書・配列・オブジェクト）、またはリテラルだけを 1 回束縛し、束縛と指定 assertion 以外で参照・再代入・変更しない名前に限る。例外を期待する形の型 `E` は組み込みの例外名、または import で束縛した名前（属性をたどったものを含む）に限る。実行器は AST から期待値を取り出し、ケース JSON の期待値と正規化した JSON（組はリスト）で一致すること、例外の場合は `E` の末尾の名前がケース JSON の期待例外の型名と一致することを確かめ、不一致なら拒否する。`assert api(x) == load_expected()`、`== mod.NEW_CONST`、`== helper(x)` のように期待値を呼び出し・属性参照・ファイル読み込みで得る形は拒否する。
   - **追加テストは対象と比較器を書き換えない**: 追加テストは、import した名前の属性・添字への代入、`setattr`／`delattr`、`monkeypatch`、`unittest.mock.patch*`、`importlib.reload` を含まない（AST で拒否）。unittest の比較器も変えさせない。追加テストでの `addTypeEqualityFunc` の呼び出し、`_type_equality_funcs`・`_getAssertEqualityFunc`・`_baseAssertEqual` への参照、テストクラスでの `assert*`・`fail*` という名前のメソッドの定義を AST で拒否する。テストクラスの基底は `unittest.TestCase` または `unittest.IsolatedAsyncioTestCase` を直接指定させる。実行時にも、指定 `self.assert*` の呼び出しの時点で、そのメソッドと、実測値と期待値の型に対して選ばれる型別比較器が標準ライブラリの元の関数であることをラッパーが確かめ、違えば未検証にする（`getattr` などで AST をすり抜けた登録もここで落とす）。Node では、テストコンテキスト `t` とそのメンバー（`t.assert` を含む）への代入を拒否する。
   - **入口の実引数の照合**: 入口への進入時（§4.3 の条件 C で記録する進入）に、各引数の値（名前は指定 assertion の位置にある追加テストのフレームから読み、リテラルは AST から得る）を、型の印を付けた正規化 JSON（§4.2-1 の `{"type", "value"}` 形式）に直列化して記録する。直列化できる値と型名は、Python は組み込みの厳密な型（`type(v) is ...`。サブクラスは直列化不能として除外）で `None`（`none`）・真偽（`bool`）・整数（`int`）・有限の浮動小数（`float`）・文字列（`str`）・バイト列（`bytes`。値は base64）と、それらを要素に持つリスト（`list`）・組（`tuple`）・文字列キーの辞書（`dict`）、Node は `undefined`・`null`・真偽（`bool`）・有限の数（`number`）・`BigInt`（`bigint`。値は 10 進の文字列）・文字列（`str`）と、それらを要素に持つ通常の JSON 相当の配列（`array`）・プレーンオブジェクト（`object`）とする。Node で到達した全 `array`・`object` は、`Proxy` でないこと（`!util.types.isProxy(v)`）、厳密なプロトタイプを持つこと（`array` は `Object.getPrototypeOf(v) === Array.prototype`、`object` は `Object.getPrototypeOf(v) === Object.prototype`。`Object.create(null)` やサブクラスを除外）、拡張可能であること（`Object.isExtensible(v) === true`。`Object.freeze`・`Object.seal`・`Object.preventExtensions` を除外）、Symbol キーを持たないこと（`Object.getOwnPropertySymbols(v).length === 0`）を必須とする。さらに、Node の `object` は全独自プロパティ（`Object.getOwnPropertyNames(v)` の列挙順）が `writable: true`・`enumerable: true`・`configurable: true` のデータプロパティ（`"value" in desc`。getter／setter のアクセサは呼ばずに除外）であること、`array` は `length` が `writable: true` であり、`0`〜`length - 1` の全添字が存在し（疎配列を除外）各添字が `writable: true`・`enumerable: true`・`configurable: true` のデータプロパティでそれ以外の独自プロパティを持たないこと（`Object.getOwnPropertyNames(v).length === v.length + 1`）を必須とする。辞書（`dict`）・オブジェクト（`object`）の `value` は `[キー, 型付き値]` の組の配列とし、Python は辞書の挿入順（`list(d.items())` の順）、Node は `Object.getOwnPropertyNames(v)` の列挙順（通常のプレーンオブジェクトでは `Object.entries` と同じ順。値は `Object.getOwnPropertyDescriptor(v, k).value` から読む）を保存してそのまま比べる（キーは整列しない。重複キーは拒否し、追加テストの辞書・オブジェクトリテラルでも重複キーを AST で拒否する）。`kwargs` も `[引数名, 型付き値]` の組の配列とし、呼び出し時のキーワード引数の並び順を保存して比べる（Node は空配列）。これらを満たさない値（Python の組み込み型サブクラス、Node の凍結・封印・拡張不可・書き込み不可／削除不可プロパティ・アクセサ・非列挙プロパティ・Symbol キー・疎配列・配列の余剰プロパティ・`Proxy`・`Object.create(null)` 等を含む）は直列化不能として未検証にする（変更前なら「実行・環境エラー」、変更後と最終なら登録しない「実行エラー」、登録済みの再実行なら合格に数えず `openFailures` に残す）。あわせて、直列化時に `args` と `kwargs` の全要素を再帰的にたどり（Python の `tuple` の中身を含む）、到達した可変コンテナ（Python は `list`・`dict` の `id`、Node は `array`・`object` のオブジェクト同一性 `===`）の重複を検査する。同一の可変コンテナが 2 か所以上に現れる場合（例: 同じ空リストを二引数に渡す `x = []; api(x, x)`、位置引数とキーワード引数で共有する、コンテナや `tuple` の内側で共有する、循環参照を含む）は、参照共有しない別コンテナと同一の JSON になり前後で合否が反転し得るため、直列化不能と同様に未検証とする（変更前なら「実行・環境エラー」、変更後と最終なら登録しない「実行エラー」、登録済みの再実行なら合格に数えず `openFailures` に残す）。不変値（`None`／`null`／`undefined`・真偽・数値・文字列・`bytes`、および中身に可変コンテナの共有がない `tuple` 自体）の共有は拒否しない。変更前・変更後・最終の各実行で、可変コンテナの参照共有や上記の直列化不能・通常 JSON 外属性がなく、かつ直列化値がケース JSON の `input`（位置引数とキーワード引数の並び・対応を含む）と型・順序まで一致することを要する（変更前に入口がない「公開入口なし」では変更後と最終だけを照合する）。一致しない実行は、変更前なら「実行・環境エラー」、変更後と最終なら登録しない「実行エラー」（登録済みの再実行なら合格に数えず `openFailures` に残す）とする。例えばケース JSON の入力が空文字なのに追加テストが `api("abc")` を呼ぶ場合、`"abc"` の前後差は空文字の境界証拠にならず未検証になる。整数の `1` と真の `True`、整数の `1` と浮動小数の `1.0` も型が違うため一致しない。キーの集合と各値が同じでも挿入順やキーワード引数の並びが異なる実行（例: ケース JSON が `[["b", 1], ["a", 2]]` なのに `{"a": 2, "b": 1}` が渡る場合）も入力不一致となり証拠から外れる。片方を更新して他方を読む入口で、準備時の参照共有だけが変わるケース（`api(x, x)` と `api([], [])`）も共有側が未検証になり証拠から外れる。引数を更新する Node の入口に対し、準備処理が `Object.freeze({x: 1})` と通常の `{x: 1}` を切り替えて成否を反転させるケースや書き込み不可プロパティを持つ入力も、凍結・書き込み不可側が未検証になり証拠から外れる。実装から読んだ値で入力を作る場合など、実行によって値や順序が変われば未検証になる。
   - **入力に使うデータファイルとコピー内ファイルの参照（`inputFiles`・存在確認と権限およびパス操作の捕捉・既存非保護ファイルの固定）**: `inputFiles` に列挙したファイル（新規または変更前から存在する保護対象外の非コードファイル）は、追加テストと同じく、変更後スナップショットから採取した同一バイト列・同一権限ビット（`st_mode & 0o777`）を前後双方のコピーへ配置する（§4.4）。登録時にバイト列のダイジェストと権限ビットを固定し（§4.2-2）、以後の実行で配置したファイルのダイジェストまたは権限ビットが固定値と異なれば合格に数えない。さらに、追加テストの実行中（追加テストファイル自身、親プロセスのモジュール読み込み［Python は `importlib`、Node はモジュールローダ内部］、ランナー・トレースバックの内部処理を除く）に、入口の内側・外側（および下記により捕捉した子孫プロセス）を問わずコピー内のパスへ行った **読み込み・存在確認・`stat` 系・権限確認（`access` 系）・ディレクトリ一覧取得に加え、削除（`unlink`・`rmdir`・`rm`）・作成（`mkdir`・書き込み／排他作成を含む全 `open`）・移動／リンク（`rename`・`link`・`symlink`）・属性／サイズ変更（`chmod`・`chown`・`utime`・`truncate`・`xattr`）・作業ディレクトリ移動（`chdir`）など、戻り値や例外からパスの存在・種別・権限を判別できるすべてのコピー内パス操作**（操作が `ENOENT`・`EEXIST`・`EACCES`・`ENOTEMPTY` 等で失敗した場合も対象パスを捕捉し、`rename`・`link` は変更前後の両パス、`symlink` は作成先パスを対象にする）と、実引数の文字列が指すコピー内パスをすべて捕捉する。捕捉した各コピー内パスについて、実行開始時点（`inputFiles` 配置後）のコピーにおける **スナップショット初期状態**（不在、通常ファイルの種別・権限ビット［`st_mode & 0o777`］・内容の SHA-256、シンボリックリンクの種別・リンク先と参照先が存在すれば参照先の種別・権限ビット［`st_mode & 0o777`］・通常ファイルなら内容の SHA-256、ディレクトリの種別・権限ビット［`st_mode & 0o777`］と、一覧取得またはディレクトリ削除・上書き移動［`rmdir`・`AT_REMOVEDIR` 付き `unlinkat`・`rm`・既存ディレクトリを移動先とする `rename` 等］の場合は `__pycache__` を除く直下項目名の整列一覧。さらに `os.access`・`fs.access`・`fs.accessSync`・`faccessat*` 等で確認したパスについては、開始時点のコピーにおける確認対象権限［`R_OK`・`W_OK`・`X_OK`］の可否も初期状態に含める）を求める。例外として、すでに読み込まれているコードモジュール自身の `__file__` に対する存在確認・`stat`・`lstat`・`access`・`readlink` は `Path(__file__).resolve()` 等の慣用を妨げないよう存在・種別・権限ビット（`st_mode & 0o777`）・確認権限の可否・リンク先だけを記録し内容の SHA-256 は含めない（`open`／内容読み込みは常に内容の SHA-256 を記録する）。捕捉したパスが、(a) `inputFiles` に列挙していない、変更前スナップショットに存在せず変更後スナップショットに存在するパスである場合、または (b) 変更前コピーと変更後コピーでスナップショット初期状態が異なる場合（変更前から存在する非保護ファイルを `inputFiles` に列挙せず書き換え・権限変更［`chmod +x` 等］・削除した場合を含む）は、同一入力での前後比較にならないため、変更前なら「実行・環境エラー」、変更後と最終なら登録しない「実行エラー」（登録済みの再実行なら合格に数えず `openFailures` に残す）とする。変更前後のどちらのスナップショットにも存在しないパスを実行中に作って読み返したり削除したりする場合は、双方の初期状態が「不在」で一致するため拒否しない。登録時には、捕捉した全コピー内パスのスナップショット初期状態（権限ビット・確認した権限および該当時のディレクトリ項目一覧を含む）を台帳に固定する（§4.2-2）。以後の変更後実行と最終実行では、固定した全パスのコピー内スナップショット初期状態を直接照合し、1 件でも固定値と異なれば（変更前から存在する非保護ファイルを登録後に易しい内容へ書き換える・実行ビット等の権限を変える・削除する、または不在だったファイルを新設する場合を含む）合格に数えず `openFailures` に残す。これにより、未列挙の新規ファイルによる `FileNotFoundError` や存在確認・権限確認（`os.access(path, os.X_OK)` 等）・削除（`unlink` の成功と `ENOENT` 等）だけの前後差（識別子から内部でパスを組み立て `Path.exists()`・`os.path.exists`・`os.stat`・`os.access`・`os.unlink` 等で結果を返す場合を含む）を期待値不一致に数えず、新規・既存を問わず登録後のデータファイル新設・書き換え・権限変更・削除で失敗を消す経路も閉じる。親プロセスの捕捉手段は、Python では対象モジュールと追加テストの読み込みより前にプラグイン／ラッパーで `sys.addaudithook`（`open`・`os.listdir`・`os.scandir`・`glob.glob`・`os.remove`・`os.rmdir`・`os.rename`・`os.mkdir`・`os.chdir`・`os.chmod`・`os.chown`・`os.utime`・`os.truncate`・`os.link`・`os.symlink`・`os.getxattr`・`os.listxattr`・`os.setxattr`・`os.removexattr`）に加え、`os.stat`・`os.lstat`・`os.access`・`os.readlink` および `pathlib.Path.stat`・`pathlib.Path.lstat`・`pathlib.Path.exists` をラップして捕捉する（`dir_fd` 付き呼び出しは Linux の `/proc/self/fd/<dir_fd>` で解決し、解決不能なら未検証。整数 fd の `os.stat(fd)` 等は `open` 時に捕捉済みのため除外）。Node ではコピー外 preload で `fs` と `fs/promises` `process.chdir` を包み（ESM の名前付き import にも反映するため `module.syncBuiltinESMExports()` を呼ぶ）捕捉する。いずれも実引数の文字列が指すコピー内パスの照合を併用する。

   **新規モジュール不在の受入例**: いずれも、エラーを起こした読み込みが追加テストファイル自身の import／require 文であることを要する（Python はトレースバックのうち importlib を除く最も内側のフレーム、Node は ESM の読み込み元と CommonJS の `requireStack[0]` で確認する）。対象モジュールの読み込み中に別の依存が見つからない場合は実行エラーとする。
   - Python・パッケージ配下（`pkg.new_mod`）: `ModuleNotFoundError` の `name` が `pkg.new_mod` に一致し、親パッケージ `pkg.__file__` の実パスが変更前コピー内にある。
   - Python・トップレベル（`new_mod`。記録すべき親 `__file__` がない）: `ModuleNotFoundError` の `name` が `new_mod` に一致し、`sys.path` の先頭がコピーと公開 `src` ルート（いずれもコピー内）であることを記録できる。
   - Node・ESM: `ERR_MODULE_NOT_FOUND` で、見つからなかったパスの解決結果が変更前コピー内の対象パスに一致する。
   - Node・CommonJS: `require` の `MODULE_NOT_FOUND` で、`err.requireStack[0]` が変更前コピー内の追加テストファイルの実パスに一致し、要求した相対指定を追加テストファイルの位置から解決した候補パスが変更前コピー内の対象パスに一致する。

5. **既存公開テストの前後比較と同一条件再実行**:
   - 依頼開始時（前）と検証時（後）の隔離コピーで、既存の公開テスト一式を同一条件・同一順序で実行し、テスト識別子ごとの合否を記録する。前後とも、開始時に存在したテストファイルだけを明示パスで実行し、依頼中に新設したテストファイルは同じ実行に含めない（Python・Node の既存テストファイル集合は §6.3 の定義による）。
   - 開始時に合格したテストが変更後に失敗した場合、**単独再実行は行わない**。残り予算内で新しい変更後隔離コピーを作り、**初回と同一のテスト集合・同一順序でスイート全体を 1 回だけ再実行**する。2 回目も失敗なら「新規回帰（未検証）」、2 回目で合格すれば「不安定（両回結果を記録し新規回帰に数えない）」。
   - 収集エラー、ランナー異常終了、予算不足による再実行未完、開始時合格テストの個別結果が 1 件でも照合不能な場合は、理由を記録して「未検証」とする。

### 4.3 3 ランナーの隔離実行と assertion 到達計測

全ランナー共通で、指定 assertion について次の 2 条件を**別々に**記録し、両方の成立を必須とする。

- **条件 L（対象モジュールのロード）**: 対象モジュールの読み込み元実パス（Python `os.path.realpath(module.__file__)` / Node `fs.realpathSync(解決結果)`）が前後それぞれ対応する隔離コピー内にある（新規モジュール不在は §4.2-4 の受入例で扱う）。
- **条件 C（公開入口の呼び出し）**: 指定 assertion の評価中に、公開入口の関数本体へ実際に入った。具体的には、入口の関数への進入のうち、呼び出し元をたどって最初に見つかる追加テストファイルのフレームの実行位置が指定 assertion の範囲内にあるものが 1 件以上ある。入口の関数は、追加テストで束縛した入口名が指す関数（デコレータやラップ、再エクスポートの場合は、その名前が指す外側の関数）とする。モジュールが読み込まれただけ、入口名が解決できただけ、準備の文や準備用ヘルパーが間接的に入口を呼んだだけでは成立しない。指定した比較の評価中の進入を確認できない場合（計測手段が使えない版を含む）は未検証とする。例外を期待するケースでは、C の成立と §4.2-3 の「例外の出所」を合わせて、例外が指定した公開呼び出しから出たことの証拠とする。

### 4.4 前後のスナップショットと台帳

- **変更前**: 依頼開始 hook 時点で、作業ツリー（ステージ済み・未ステージ変更、`.gitignore` 対象外の未追跡ファイル、および任意の `includePaths`）の内容・権限ビット（`0o777`）・リポジトリ内参照に限ったシンボリックリンク先からスナップショット ID を算出し固定する。作業ツリーや Git index を改変せず、依頼途中のコミットでも基準を更新しない。
- **変更後**: `verify-diff` 実行時および Stop 照合時に同一規則で採取する（未コミット変更・未追跡ファイル・削除を反映）。
- **隔離コピー**: リポジトリ外の `os.tmpdir()` 配下に依頼 ID 別の作業領域を作り、`realpath` がリポジトリ外であることを確認して毎回前後を展開し、スナップショットの権限ビット（`0o777`）を再現する（削除時は `chmod -R u+w`）。変更後から採取した同一バイト列の追加テストと、同一バイト列・同一権限ビット（`0o777`）の `inputFiles`（§4.2-1。変更前から存在する非保護ファイルが含まれる場合は変更前コピー側も同バイト列・同権限ビットで上書きする）を前後双方に配置する。
- **台帳**: 状態・依頼文・ケース JSON・ケースの固定ダイジェスト・取り下げ記録・実行記録は作業ツリー外の Git 管理領域（`git rev-parse --git-path claude-verify` 配下）に保存し、追記自体はスナップショット ID を変えない。検証後に実装または追加テストが変化すれば、最終 Stop 時の ID 照合で旧証拠は自動的に失効し、介入済みなら「未検証（検証後の変更）」で終了する。

### 4.5 保護対象と意味単位（AST）の差分検査

文字列・行単位の差分禁止は正当なテスト追加を誤検出するため（資料 F の教訓）、Verify の保護検査と評価側の改ざん診断は**共通の意味単位（AST・構造解析）規則**を、**同じ実装と同じテスト用コーパス**で使う（§7 作業 1・2d・4）。保護検査で違反があれば有効な証拠を発行せず、既存証拠も照合不可とする（評価側での扱いは §6.2）。

- **既存テストファイルと既存 conftest.py（否定列挙）**: 開始時に存在した束縛・本体・デコレータを変えない追加は、下の禁止に当たらない限りすべて許可する。許可の例は、新しい `import` 行、既存 `import` への名前追記、新しいテスト関数・テストメソッド・テストクラス、補助関数・定数、autouse でない fixture である。禁止するのは次の 4 種だけとする。
  1. **既存要素の変更**: 開始時に存在したテストファイル・テストクラス・テスト関数／メソッド・fixture の削除・リネーム、本体・引数・デコレータ（`skip`/`xfail` 等）の変更、既存のモジュール変数・クラス属性・import 名の束縛の変更・削除。

  - 不合格に数える改ざんは、無力化処理を適用できない場合に限る（例: 構文が壊れていて項目単位の復元ができない設定ファイル、復元対象を特定できない変更）。
  - PREREG 本体が改ざんとして不合格に数える変更（既存のテストの削除・確認の正味の減少・既存のテストへの skip・設定で対象を狭める）は、いずれも無力化処理で消える。追補 B は不合格に数える範囲を上記に絞る数え方の固定であり（追補 A と同じ種類の固定で、判定表は変えない）、較正の開始前にコミットして、較正（追補 B-0 の集計）と本番で同じ定義を使う。これにより、Stop の理由文で保護規則を教わる P2 と教わらない P0 の間で、改ざんによる不合格が P0 に偏ることを防ぐ。
  - `tamper_check` は Verify の保護検査（§4.5）と同じモジュール・同じ対コーパスを使い（§7 作業 4）、較正開始前に §4.5 の固定前ゲートで偽陽性 0 件・検出率 100% を確認・記録してから固定する。

### 6.3 P2 の配備・`verifyV2` 機械的生成規則・`unsupported` の挙動

- **P2 単体配備**: P2 は既存プロファイル（Claude `claude-verify-layer` / Codex `codex-verify-layer`）を v0.2 単体（`mode: "enforce"`, `adversarial: false`）へ差し替え、v0.1 資材は P1 に限定する。起動前に `.git/claude-verify` の不在・空、および P0 への Verify 要素・共通ルール汚染がないことを自動点検する。
- **`verifyV2` 機械的生成規則**: 評価ハーネスが各 fixture の開始時点の公開ファイル・公開設定・公開テスト実行環境のみから決定論的に生成し、入力と生成結果をログに保存する（隠し資材や試行結果による調整を禁止）。用語は次の通り。
  - **Python テストファイル**: 既定の `test*.py`・`*_test.py` に加え、公開 pytest 設定（`pytest.ini`、`pyproject.toml` の `[tool.pytest*]`、`setup.cfg` の `[tool:pytest]`、`tox.ini` の `[pytest]`）に `python_files` が指定されていれば、そのグロブに合う `.py` ファイル（`testpaths` 指定があればその配下）も含める。
  - **TestCase 形式**: AST 上 `unittest.TestCase` または `unittest.IsolatedAsyncioTestCase`（`from unittest import TestCase` などの別名を含む）を基底に持つクラス。基底がリポジトリ内の別のクラスなら import と定義をたどって解決し、解決できない基底は TestCase 形式とみなさない。
  - **pytest 形式**: トップレベルの `def test*`（`async def` を含む）、または TestCase 形式でない `class Test*`（基底なし、基底が `object` だけ、またはリポジトリ内で TestCase 形式に解決されない基底を持つもの。`class TestX(object)` を含む）の `test*` メソッド。公開 pytest 設定に `python_classes`・`python_functions` が指定されていれば、それらに合うクラス・関数も含める。
  - `import unittest` や `from unittest import mock` などの参照は判定に使わない。
  - **pytest あり**: 評価環境で `python3 -I -c "import pytest"` が成功する。
  - **Python の静的一覧**: Python テストファイル内の、TestCase 形式のクラスの `test*` メソッドと、pytest 形式のテスト（ファイル・クラス・関数の組。パラメータ化の添字は除く）。
  - **`load_tests` 定義ファイル**: 開始時点のリポジトリ内の Python テストファイル（`test*.py`・`*_test.py`）またはパッケージの `__init__.py` のうち、モジュール直下に `load_tests` の束縛（`def`・`async def`・代入・`import`）を持つファイル。
  - **Python の公開設定収集一覧**: 開始時点の隔離コピーで、「公開 pytest 設定（上記 4 種および `conftest.py`）がある」または「公開依存に `pytest` が明示されている」場合に、§4.3 と同じ隔離起動オプション（コピー内設定 `-c <コピー内設定または/dev/null>`）で `pytest --collect-only` を実行して得たテスト識別子（ファイル・クラス・関数の組。パラメータ化の添字は除く）の集合。0 件で正常終了（pytest 終了コード 5）した場合は空集合とする。公開 pytest 設定または公開依存に `pytest` があるのに `pytest` がない場合、または `pytest --collect-only` が収集エラー・異常終了した場合は **「Python 収集不能」** と記録する。
  - **Python の unittest 発見一覧**: 開始時点に `load_tests` 定義ファイルが 1 件以上ある場合に、開始時点の隔離コピーで下記の `unittest` 発見設定（`S` に `load_tests` 定義ファイルも含めて算出した `unittestStartDir`・`unittestTopLevelDir`・`unittestPattern`）により `TestLoader.discover` を実行して得たテスト識別子（ファイル相対パス・クラス名・関数名の組。ソースファイルを解決できない動的テストは `test.id()` で識別する）の集合。あわせて、ラッパー `unittest-runner.py` は `TestLoader.discover` の探索中に、検出した各 `load_tests` 定義ファイルが実際に探索対象として読み込まれ `load_tests` の参照・呼び出し段階に到達したか（他ファイルからの通常の `import` ではなく、`discover` のモジュール／パッケージ発見経由で `realpath` が一致したかを `unittestPattern` の全パターン実行の和集合で確認）を記録する。すべての `load_tests` 定義ファイルが訪問され、0 件でエラーなく終了した場合は空集合とする。発見中に例外・異常終了が起きた場合、`loader.errors` が空でない場合、発見結果に `_FailedTest`（`ModuleImportFailure`・`LoadTestsFailure` 等）が 1 件でも含まれる場合、または検出した `load_tests` 定義ファイルのうち **1 件でも未訪問が残る場合**（例: `__init__.py` のない複数ディレクトリに `test_suite.py` が分散し、共通祖先からの `discover` がそれらを訪れずエラーなしで空集合を返す場合や、リポジトリ直下の `__init__.py` に `load_tests` がある場合）は、未訪問ファイル一覧を記録して **「Python 収集不能」** とする（複数ディレクトリの同名ファイルによる `sys.modules`・`test.id()` 衝突や前後比較設定の複雑化を避け、個別発見で無理に結合せず `unsupported` に倒す）。
  - **Python の既存公開テスト集合**: 「Python の静的一覧」「Python の公開設定収集一覧」「Python の unittest 発見一覧」の和集合。§4.2-5 の pytest 前後比較で明示パス実行する開始時テストファイル集合は、この集合に含まれる全ファイルとする（`unittest` の前後比較は開始時に確定した `unittest` 発見設定で実行し、開始時点の既存テスト集合だけを対象にして依頼中に新設したテストファイルを含めない）。
  - **Python 側あり**: Python の既存公開テスト集合が空でない、または「Python 収集不能」である。
  - **Node テストファイル**: `node_modules` を除き、拡張子が `.js`・`.mjs`・`.cjs` で `node --test` の既定の探索パターン（`**/*.test.*`、`**/*-test.*`、`**/*_test.*`、`**/test-*.*`、`**/test.*`、`**/test/**/*`）に合うファイルと、`scripts.test`（推移閉包含む）の `node --test` の引数に明示されたファイル。
  - **Node の静的一覧**: 開始時点の Node テストファイルの集合。
  - **Node の既存テストファイル集合**: `package.json` の `scripts.test`（推移閉包含む）が `node --test` を呼ぶ場合に、開始時点のコピーでその呼び出し（引数を含む）を実行して reporter が記録したテストファイルの集合（ランナーの起動失敗・異常終了等で reporter がテストファイル集合を記録できなかった場合は **「Node 収集不能」** と記録する）。§4.2-5 の Node 前後比較は、この集合を明示パスで実行する。
  - **Node の既存公開テスト集合**: 「Node の静的一覧」と「Node の既存テストファイル集合」の和集合。
  - **Node 側あり**: Node の既存公開テスト集合が空でない、または「Node 収集不能」である。
  - **既存テストの全体一覧**: Python の既存公開テスト集合と Node の既存公開テスト集合を合わせたもの（他言語側を含む）。

  優先順位は次の 1 本だけとし、上から最初に当たった規則で決める。どのリポジトリにも 1 つの結果が決まる。
  1. 「Python 側あり」かつ「Node 側あり」（Python と Node の既存公開テストが同居する、または一方があり他方が収集不能）→ `runner: "unsupported"`（1 つのランナーでは他言語側の既存公開テストを前後比較できないため）。
  2. `pytest` があり、Python の既存公開テスト集合が空でなく、Python 収集不能でなく、かつ「公開 pytest 設定（`pytest.ini`、`pyproject.toml` の `[tool.pytest*]`、`setup.cfg` の `[tool:pytest]`、`tox.ini` の `[pytest]`、`conftest.py`）がある」「公開依存に `pytest` が明示されている」「pytest 形式のテストがある」のいずれかを満たす → `runner: "pytest"`（同じリポジトリの TestCase 形式も pytest で実行する）。
  3. Python 収集不能でなく、「TestCase 形式のクラスがある」または「Python の unittest 発見一覧が空でない」を満たし、pytest 形式のテストが 1 件もない → `runner: "unittest"`（pytest の有無を問わない）。
  4. 「Python 側あり」が偽（Python の既存公開テスト集合が空で、Python 収集不能でもない）で、`package.json` の `scripts.test`（推移閉包含む）が `node --test` を直接呼び、Node の既存公開テスト集合が空でなく、Node 収集不能でもない → `runner: "node"`。
  5. いずれにも該当しない → `runner: "unsupported"`。

  帰結: TestCase 形式だけのリポジトリは、公開 pytest 設定か pytest 依存があれば pytest、どちらもなければ pytest があっても `unittest`（pytest の既定の収集名に合わない `tests.py` などの取りこぼしを避けるため）。pytest がなく pytest 形式のテストがある場合は、TestCase 形式と混在していても、`node --test` が同居していても `unsupported` になる（規則 1 または 5。unittest は同居する `def test_*` や `class TestX(object)` を実行せず、Node は Python のテストを実行しないため）。公開 pytest 設定の `python_files = spec_*.py` に沿う `spec_*.py` しかない Python テスト（既定パターンの静的一覧が空）に `node --test` が同居する場合や、`scripts.test` が既定パターン外のディレクトリを実行する Node テストと Python テストが同居する場合も、公開設定に沿った収集結果（または収集不能）により「Python 側あり」かつ「Node 側あり」となるため、pytest の有無を問わず規則 1 で `unsupported` になる。また、pytest 設定・依存がなく `test_suite.py`（またはパッケージ `__init__.py`）の `load_tests` だけが別ファイルから unittest スイートを組み立てる場合も、開始時の `load_tests` 検出と `unittest` 発見結果（失敗時または未訪問残存時は「Python 収集不能」）が反映されるため、Node テストが同居すれば規則 1 で `unsupported` になり Python 側の回帰が落ちない。特に、`__init__.py` のない複数ディレクトリ（例: `suite_a/test_suite.py`・`suite_b/test_suite.py`）がそれぞれ `load_tests` だけでスイートを組み、共通祖先からの `discover` が両方を訪れずエラーなしで空集合を返す場合でも、未訪問の `load_tests` 定義ファイルの検出により「Python 収集不能」となるため、Node 同居時は規則 1 で `unsupported`、Python のみでも規則 5 で `unsupported` となる。Python のみで全 `load_tests` 定義ファイルが訪問され正常に発見できれば規則 3 で `unittest` となる。公開 pytest 設定があるリポジトリに `load_tests` が同居し pytest がそのテストを収集できない場合は、下記の網羅の確認（または未訪問による「Python 収集不能」）で `unsupported` になる。
- **網羅の確認（規則 2〜4 で選んだ場合）**: 開始時点のコピーで、選んだランナーが **既存テストの全体一覧（他言語側を含む）** をすべて実行できるかを確かめ、1 件でも落ちる場合、または他言語側の既存公開テスト（あるいは収集不能）が残る場合は `runner: "unsupported"` とし、理由と落ちた識別子またはファイルを記録する。
  - pytest: §4.2-5 と同じ明示パス（Python の既存公開テスト集合の全ファイル）を公開設定に沿って収集したテスト識別子が、既存テストの全体一覧をすべて含むこと（Node 側が空であること）。
  - unittest: 下記の発見設定でエラー（`loader.errors` や `_FailedTest` を含む）なく、かつ検出した全 `load_tests` 定義ファイルが訪問された状態で収集したテスト識別子が、既存テストの全体一覧をすべて含むこと（Node 側が空であること）。
  - node: Node の既存テストファイル集合が、既存テストの全体一覧のファイルをすべて含むこと（Python 側が空であること。例: `scripts.test` が `node --test test/unit` だけを実行し、既定のパターンに合う `test/integration/a.test.js` が残る場合や、Python 側に公開設定・`load_tests` で収集されるテスト、または未訪問の `load_tests` 定義ファイルが残る場合は `unsupported`）。
- **`unittest` の発見設定**: S を「TestCase 形式のクラスを持つ Python テストファイル」と「`load_tests` 定義ファイル」の和集合とし、次の手順で決める。
  - `unittestPattern`: S から `__init__.py` を除いた集合が空または全ファイルが `test*.py` に合えば `["test*.py"]`、そうでなく全ファイルが `*_test.py` に合えば `["*_test.py"]`、それ以外は `["test*.py", "*_test.py"]`（ラッパーはパターンごとに発見し、`test.id()` で重複を除く）。
  - `unittestStartDir`: S の各ファイルについて、通常ファイルはその親ディレクトリ、パッケージの `__init__.py`（例: `tests/__init__.py`）はその 1 つ上の親ディレクトリ（`.` 等、当該パッケージをサブパッケージとして発見できるディレクトリ）を基準ディレクトリとし、それらの最長共通祖先（リポジトリ相対。共通部分がなければ `.`）。
  - `unittestTopLevelDir`: ルート直下から `unittestStartDir` までの各ディレクトリにすべて `__init__.py` があればリポジトリルート、なければ `unittestStartDir`（`unittestStartDir` が `.` のときは `.`）。
  - 確認: 発見中にエラー（`loader.errors` や `_FailedTest` を含む）があるか、検出した `load_tests` 定義ファイルに未訪問が残るか、発見したテスト識別子が網羅の確認を満たさなければ `runner: "unsupported"` とする。
- `protectedPaths` は公開 fixture から特定したテスト専用パスを安定ソートで出力し、多用途ファイルには §4.5 の項目単位＋推移閉包保護を自動適用する。`includePaths` は未設定とする。
- **ランナー分布の記録と対応外の割合**: 追補 B 固定時に、ハーネスは held-out の全 fixture について生成した設定とランナー別の件数を、著者が閲覧しないハーネス内の領域に保存し、そのファイルの SHA-256 を追補 B に記録する。held-out の罠のうち `unsupported` の割合が **1/3 を超える**場合（6 罠なら 3 件以上）、本番を開始せず `INCONCLUSIVE（対応外過多）` とする。ハーネスは著者に超過の有無だけを返す。
- **`unsupported` 時の Stop 挙動**: Stop hook は発火して台帳に `未検証（対応外ランナー）` を記録し、**ブロックせず（追加ターンを発生させず）終了を許可する**。試行と時間・費用は層の計測に含め、共通手順で外部採点する。`unsupported` の罠での Stop 発火は、強制が機能した証拠に数えない（§6.5 の判定不能 (b)）。実セッション検証で強制モードを確認できないホストの P2 は「実施不可」として起動せず、観察モードで代用しない。
- **診断集計**: `未検証（意図した変更）`、`未検証（対応外ランナー）`、`未検証（ケース取り下げ）`、通常 `未検証` を分離集計する。対応ランナーの P2 罠での Stop 発火数・ブロック数・`verify-diff` 実行数を記録する。held-out 公開後、誤りが残った試行を「選び方の失敗」「検出の失敗」「修正未完」「ケース未選定」「記録欠落」に分類記録する。

### 6.4 費用上限・実行順序・定額プラン運用規則

- **API 課金なし**: 本評価・較正・副次判定のすべてを作業者本人の定額プラン枠のみで実行し、従量 API 課金は行わない。
- **試行ごとの共通 limits**: 全プロファイル（P0 / P1 / P2）で `max_turns`・`timeout_s`・`max_budget_usd` 相当を完全同一に固定し、v0.2 の追加ターン（最大 1 回）と `verify-diff` 実行時間も上限に含める。上限到達による停止は追補 A 通り「不合格」（無効ではない）。
- **全体上限と事前検査**:
  - 資料 D の定価換算合計上限 **$35 相当**（Claude 上限 $16、Codex 上限 $10、盲検副次判定上限 $8）を守る。較正費用は追補 B-0 通り別計上とする。
  - 本番の開始前と各チャンクの開始前に、ホスト別に「試行ごとの上限 `max_budget_usd` × 残りの試行数 ≤ ホストの残予算」を、副次判定は「1 件あたりの上限 × 残りの判定数 ≤ 副次判定の残予算」を確かめ、満たさなければ開始しない。例: Claude の 81 試行で、試行上限 $0.19 なら 81 × 0.19 = $15.39 ≤ $16 で開始できる。$0.20 なら $16.20 > $16 で開始しない。上限値の見直しは、結果を見る前の新しい追補として記録する。
  - 実行中にホストの定価換算累計がホスト上限に達したら、そのホストの新規投入を止める（実行中の試行は完走・記録する）。その時点で未実行の試行が残っていれば、そのホストの判定を `INCONCLUSIVE（予算）` とする。全予定試行が完了した時点で上限にちょうど達した場合、または最後の試行の完走中に達して未実行が 0 件の場合は、予算による判定不能にせず通常の判定（§6.5.3 の 2 以降）を行う。副次判定の予算に達したら副次判定だけを止めて未実施を記録する（主判定に使わないため判定は変わらない）。
- **実行順序（追補 B に固定）**:
  - 実行の単位は「組」とする。組は同じホスト・同じタスク（罠または対照）・同じ試行番号の P0・P1・P2 の 3 試行である。チャンクは組の並びの連続区間とし、組の途中では区切らない。
  - ハーネスは追補 B に記載する固定 seed で、ホスト別に組の順序と組内のプロファイル順を生成する。その一覧（タスクは著者に内容が分からない不透明な ID で表す）を追補 B に入れ、実行はこの順に従う。
- **プラン枠の停止・チャンク規則**:
  - 各チャンク開始前に Claude 5h 枠使用率が **45% 以下**（Codex も直近枠に十分な余力がある状態。数値化は §9 に延期）であることを確認して開始する。
  - 7d 枠使用率が **88% を超えた時点**で新規の組の投入を停止する（実行中の組の残りの試行は完走・記録する。最大 3 試行）。

### 6.5 判定手続きと架空の結果表による事前検証

同じ結果表から必ず同じ判定が出るよう、判定はホスト別に次の手続きだけで行う。本実行前に評価ハーネスの判定スクリプトへ架空の結果表（試行単位の合成 JSON）を投入し、§6.5.4 の全例が期待どおりになることを自動テストで確認・保存する。

#### 6.5.1 入力

- **試行単位の行**: `host`、`task`（不透明 ID）、`kind`（`trap`/`control`）、`profile`（P0/P1/P2）、`trial`（1〜3）、`status`（`PASS`/`FAIL`/`INVALID`）。P2 だけ `runner`、`stop_fired`、`stop_blocks`、`verify_diff_runs` を持つ。上限到達による停止は `FAIL`、agent_error・利用上限・leak INVALID は `INVALID` とする（追補 A）。
- **実行単位**: 予定試行数 `N`、予算上限で停止したかどうかと未実行の試行数、対応外の割合の事前検査結果、副判定の結論（sound-eval の `conclusion`）。

#### 6.5.2 数え方（整数で比べ、丸めない）

- **有効率**: 有効試行数 `V`（全プロファイル・罠と対照）について、`4V ≥ 3N` なら充足とする（75% ちょうどは充足）。
- **P0 罠合格率**: P0 罠の有効試行数 `v0`、合格数 `p0` について、`v0 ≥ 1` かつ `5·p0 ≥ v0` かつ `5·p0 ≤ 4·v0` なら範囲内とする（20%・80% ちょうどは範囲内）。
- **罠の合格数**: `p0`・`p2` は各プロファイルの有効な罠試行の合格数とする（追補 A どおり、分母はそろえない）。
- **対**: 同じ罠・同じ試行番号の P0 と P2 で、両方が有効なものだけを数える。改善 = P0 `FAIL` かつ P2 `PASS`、後退 = その逆。片側だけ `INVALID` の対は改善・後退に数えない（有効な側の合否は合格数に入る）。対照の後退も同じ対で数える。
- **強制の機能**: `runner` が対応ランナー（`unsupported` 以外）の、有効な P2 罠試行について、`stop_blocks + verify_diff_runs` の合計を数える。`unsupported` の罠での Stop 発火は数えない。
- **副判定**: agent-harness-eval の sound-eval に、P0 と P2 の有効試行の隠しテスト合否だけを渡す（LLM 判定は渡さない）。規則は baseline を P0、candidate を P2、対照を対照タスクとし、その他は既定値（タスクでクラスタした 2 段ブートストラップのパーセンタイル区間、信頼度 0.95、10,000 回、seed 0）とする。規則ハッシュと agent-harness-eval のコミットを追補 B に記録する。結論が `IMPROVED`（区間の下端が 0 より上）のときだけ、主判定の「有用」と整合するとみなす。

#### 6.5.3 判定の順序

上から順に調べ、最初に当たった判定を最終判定とする。判定不能の条件と有用でない条件が同時に立つ場合は判定不能を優先し、成立したすべての条件を判定記録に併記する。配備するのは最終判定が `USEFUL` のホストだけである。

1. 予算上限で停止し、未実行の試行が残った → `INCONCLUSIVE（予算）`（全予定試行が完了していれば、上限に達していても当たらない）
2. 対応外の割合が 1/3 を超えた → `INCONCLUSIVE（対応外過多）`
3. `4V < 3N` → `INCONCLUSIVE (c)`
4. P0 罠合格率が範囲外 → `INCONCLUSIVE (a)`
5. 強制の機能の合計が 0（対応ランナーの有効な P2 罠試行が 0 件の場合を含む）→ `INCONCLUSIVE (b)`
6. 主判定: `p2 > p0`、改善 > 後退、対照後退 = 0 をすべて満たせば主判定 `USEFUL`、それ以外は主判定 `NOT_USEFUL`
7. 主判定 `USEFUL` かつ副判定 `IMPROVED` → 最終 `USEFUL`（配備可）。主判定 `USEFUL` で副判定がそれ以外 → 最終 `NOT_USEFUL`（副判定不一致。両方を記録し配備しない）。主判定 `NOT_USEFUL` → 最終 `NOT_USEFUL`（副判定が `IMPROVED` なら不一致として両方を記録する）

## 8. リスクと未決事項

1. **境界選定の質（選び方の失敗）**: 候補列挙と選定理由を強制しても、モデルが実装の真の誤り箇所ではなく無関係な境界を選べばバグを逃す。同一コンテキスト 1 ターン介入の限界であり、本評価で「選び方の失敗」が支配的なら次段で敵対段（fresh-context）を別事前登録で検討する。
2. **指定 assertion の記述制約と構文カバレッジ**: 指定 assertion の形（テスト本体直下の 1 文、入口の直接呼び出し、引数は名前とリテラル、期待値はリテラル、例外期待の形、Node の `await` の位置）を外れる記法や、直列化できない引数（クラスのインスタンス、関数、ファイルハンドル、Python の組み込み型サブクラス、Node の凍結・書き込み不可プロパティ・アクセサ・`Proxy` 等を持つオブジェクト／配列）・可変コンテナの参照を共有する引数を渡すケース、準備済みオブジェクトのメソッドを入口にするケース、`unittest` で独自ヘルパー関数越しに `self.assert*` を呼ぶ記法は未検証になる。SKILL と Stop 理由での案内とテンプレートが不可欠。JS パーサは作業 2d の冒頭で確定する。
3. **スイート全体再実行の予算圧迫**: 順序依存回帰の見逃しを防ぐため単独再実行を廃止した結果、実行時間の長い既存スイートで不安定テストが出ると、再実行だけで共通 `timeout_s` を圧迫し「予算不足による未検証」が増えるおそれがある。
4. **`node_modules` 独立コピーの上限（512MB）**: 大規模 Node リポジトリでは隔離上限超過で未検証になり得る。rootless な OverlayFS 等による軽量 RO 隔離は将来の拡張課題とする。
5. **ホスト CLI の Stop hook 互換性**: Claude Code・Codex のアップデートや sample-harness 併用時の `stop_hook_active` 挙動、依頼文の取得可否は作業 5 の実セッション検証まで確定しない。片側ホストが「実施不可」となるリスクが残る。
6. **自己申告区分の過大申告**: モデルが自分の誤りによる既存テスト失敗を `未検証（意図した変更）` と申告する、または未解消のケースを安易に取り下げて `未検証（ケース取り下げ）` で終了する可能性がある。評価の合否は外部隠しテストで決まるため実験は歪まないが、実運用時は別集計比率を監視する必要がある。
7. **定額プラン枠による評価期間の延伸**: 5h 45%・7d 88% の停止規則により、全 162 試行と副次判定の完了に複数日〜週単位を要し、途中でホスト CLI やモデル更新が混入するリスクがある。組単位のチャンクで P0・P1・P2 を同じ時期に流して影響を対比較の両側にそろえ、各チャンクでバージョンを記録し、変更があれば評価ログに明示する。
8. **字句照合による入口追加の取りこぼし**: 依頼文が入口名を挙げずに機能追加を求める場合、同名の定義が変更前のどこかにある場合（別クラスの同名メソッドを含む）、追加を求める文に否定語が含まれる場合（「直すのではなく `parse_v2` を新設」や丁寧な依頼の「追加してくれませんか」など）、入口の種別語や呼び出し表記・拡張子がない裸の名前だけの文（「`parse_v2` を追加する」など）、名前・種別語と追加の語が決まった語順の型に合わない場合（「`parse_v2` という関数を作る」など）、同じ文に既存の定義名や「既存」が現れる場合（「`parse` と同じ形式で関数 `parse_v2` を追加する」など）、あるいはシンボル追加の依頼文に複数の異なる非テストソースパス（参照元と配置先など）が併記され単一の配置先へ一意に絞れない場合、「公開入口なし」の証拠は未検証になる。形式名・選択肢名・別ファイルへの配置との取り違えや誤った「検証済み」を防ぐための意図した保守側の扱いであり、別集計の比率を監視する。
9. **ケース固定による上限の消費**: 期待値を直すたびに新しい `caseId` が要るため、上限 3 件に早く届き得る。入口到達前の失敗は固定しないことで、書き損じによる消費は抑える。
10. **Node の条件 C の計測**: preload とインスペクタ（worker スレッドからの `connectToMainThread()`）に依存するため、使えない Node の版や実行環境では未検証になる。ブレークポイントと例外停止で追加テストの実行時間が延び、共通 `timeout_s` を圧迫するおそれがある。
11. **入口内での子プロセス起動と非同期呼び出しの保守性**: 非同期の入口から呼んだ別の非同期関数が `await` の後で外部プロセスを起動する場合、再開時の呼び出し履歴に入口が現れず「入口の外」と判定されて未検証になることがある（Python・Node とも）。また、入口内で子プロセスを起動するケースでは、`strace` が使えない・`ptrace` が許可されない環境、トレースの解決不能時、あるいは子プロセスがリポジトリ内の変更済みコードファイル自体を読み込む場合（前後状態不一致）はいずれも保守側（未検証）に倒れる。なおコピー内ファイルの参照・固定は入口の内側・外側を区別せず一律に扱う。
12. **Python と Node の同居リポジトリ**: Python のテストと `node --test` のテストが同居するリポジトリは、どちらのランナーでも他言語側の既存テストを前後比較できないため `unsupported` になる。公開 pytest 設定があるのに `pytest` がない場合や収集エラーになる場合、および `load_tests` が収集不能または未訪問（`__init__.py` のない複数ディレクトリへの分散等）になる場合も同様に `unsupported` になる。held-out にこの種のリポジトリが多いと、対応外の割合の事前検査（§6.3）で `INCONCLUSIVE（対応外過多）` になり得る。
13. **データファイルの前後同一性・登録時固定による保守性**: 入口が新しいデータファイルを読むケースで `inputFiles` の列挙を忘れると実行エラーとして返る（同じ `caseId` で直せる）。また、変更前から存在するデータファイル（変換表・設定データ等の非コード資産）自体の内容や権限ビットを修正する依頼では、入口がそのファイルを読む・権限確認すると前後でスナップショット初期状態が変わるため実行エラーになり未検証となる（`inputFiles` に列挙すると前後同一になって差分が出ない）。登録後の書き換え・権限変更や未列挙ファイルによる見かけの前後差を防ぐための保守側の扱いである。

  - 入口追加の配置先を依頼文全体から照合: 「公開入口なし」の有効条件 (iv) で、新規シンボル（および新規モジュール）についても `entryAdditionQuote` の外を含む依頼文全体から配置先候補（ソースファイルパス表記・拡張子付きソースファイル名・リポジトリ内に存在するドット区切りモジュールパス。開始時の既存公開テストファイルのみを指す表記は除外）を抽出し、変更後に条件 L でロードした対象モジュールのリポジトリ相対パスが全候補と一致することを必須とした。一致しない場合（複数パス矛盾を含む）は観測記録に留め未検証とする（1）。
