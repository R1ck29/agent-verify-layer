# Verify v0.2 設計 rev2

v0.2 は、コード変更を終える前に、利用者の依頼から選んだ境界条件を公開入口で一つ検証する。最初の実装は Linux 上の Claude Code と Codex、`pytest` と `node --test` に絞る。ランナーは fixture ごとに明示する。敵対的な見直し、ランナーの汎用自動検出、Windows 対応は後段に回す。

## 1. v0.1 で分かったこと

E1b（旧 dev の罠 6 件と対照 4 件）の Claude の罠では P0 9/12、P1 10/12、P2 9/12 だった。P2 で verify スキルが呼ばれたのは 4/12 で、コミット後の hook は観察モードで記録するだけだった。Codex は P2 の全 6 試行で `mark verify` が実行されたが、P1 と同じ 5/6 だった。テストを複数回実行した試行でも、依頼された振る舞いの境界を確認できていなかった。また、旧 P0 は fixture 内の verify スキルを参照できた。

最初の評価では、層を外した今回の P0 と、終了前に追加テストを求める P2 を比べる。旧 dev の成績は経緯として扱う。

## 2. 最小版の仕様

### 2.1 終了時の介入

- 対象は、依頼開始時から終了時までに対象コードの差分がある依頼。コミットの有無を問わない。ドキュメントだけの変更は対象外とする。
- 利用者の依頼を受けた時点で、ホストセッション内で一意な依頼 ID を発行して変更前の状態を保存する。Stop hook による継続では同じ ID を使う。次の利用者の依頼で初めて ID を更新する。依頼開始を識別できない場合は強制モードの有効化条件を満たさない（§3.3）。
- `enforce` では、対象の依頼に現在のスナップショットの有効な証拠がなければ、Verify が発生させる追加ターンを **1 依頼につき最大 1 回**に制限して、§2.2 の手順を Stop の理由として渡す。ブロックを返す前に依頼 ID 単位で介入済みを記録する。再検証は同じ追加ターン内で行える。
- `stop_hook_active` が真なら、他の Stop hook が継続させた場合も含めて、Verify はブロックしない。これが真でも偽でも、介入済みの依頼への再ブロックは行わない。追加ターンでテスト後に実装を直した場合は、修正後の状態に有効な証拠があるかを最終 Stop で照合する。証拠がなければ「未検証」と記録する。
- `observe` は終了時の状態だけを記録する。`off` は v0.2 を無効にする。hook が失敗した場合は継続を要求せず、記録できる場合は「未検証」と失敗理由を残す。観察・強制の両方で「未検証」とともに、確認できた理由（証拠なし、状態の変化、実行失敗、予算打ち切りなど）を記録する。外側の実行器による打ち切りは実行器にも残す。v0.1 のコミット hook は従来の記録用とする。

### 2.2 依頼から証拠を作る

1. 依頼の文言から、利用者が使う **公開入口一つ、高リスクな境界入力一つ、明示した期待値一つ** を選ぶ。ケースに依頼の該当箇所、入口とその呼び出し方、入力、期待値、対応するテスト識別子を記す。境界の候補には、入力の大きさや形、文字や表記、処理順、失敗時の応答がある。依頼や許可された公開仕様から期待値を定められるケースを選ぶ。
2. 公開入口を実際の呼び出し方で動かし、観測結果と期待値を比較する assertion を持つテストを新規ファイルに追加する。既存のテスト、共通 fixture、テストの発見や実行に関わる設定は §2.4 に従って保護する。
3. `vl.js verify-diff --case <JSON>` は、指定した同じ追加テストを前後の隔離コピーで実行する（§2.3）。ケース JSON は対応づけの入力とし、合否はランナーの実行結果とケースの assertion 記録から判定する。各側の実行件数、指定ケースの状態、終了結果を保存する。変更後は、対象ケースが実行され、指定の assertion を通過し、ランナーもそのケースの成功を報告した記録が必要。収集しただけ、0 件、skip・todo・xfail、途中終了、assertion 到達なしは未検証とする。
4. 変更前の結果は次のように扱う。公開入口の不在は対象の入口を直接確認して分類する。一般の import 失敗や起動エラーは実行エラーに含める。

   | 変更前の結果 | 証拠としての扱い |
   |---|---|
   | 対象の assertion が期待値との不一致を検出 | 変更後に同じ assertion が合格すれば、その境界で起きていた不一致を確認できる |
   | 公開入口なし | 変更後の合格と合わせて、入口の追加と変更後の振る舞いを確認できる。境界の不具合を変更前に再現できたとは扱わない |
   | 収集・依存関係・実行環境などのエラー | 変更前の比較は未検証 |
   | 期待値に一致 | 変更後の振る舞いは観測できたが、そのケースで変更による差は未検証 |

5. 変更後に assertion が合格し、変更前が「期待値との不一致」または、入口の追加を求める依頼での「公開入口なし」なら、選んだケースを検証済みとする。各結果の分類はそのまま保存する。既存の確認手順も実行し、追加ケースの前後比較とは別に結果を残す。

### 2.3 前後のスナップショットと台帳

- **変更前**は、利用者の依頼を受けて作業を始める時点の作業ツリー。開始時点にあったステージ済み・未ステージの変更、Git の除外設定に該当しない未追跡ファイルに加え、開始前に `includePaths` で対象に指定したファイルは Git の除外設定にかかわらず含める。作業ツリー上の内容で固定し、利用者の変更を退避・初期化せず、依頼途中のコミットでも基準を更新しない。取得に失敗した場合は比較を未検証とする。
- **変更後**は、検証コマンド実行時に同じ規則で採取した作業ツリー。未コミットの実装と未追跡の追加テストも含む。追跡対象の削除も反映する。`HEAD` や index の内容を代用しない。
- パス、ファイルの内容と実行属性、許可されるシンボリックリンクの参照先から、コピーした内容を識別する。リポジトリ外を指すリンクはたどらない。二つの隔離コピーを作り、変更後から採った同一バイト列の追加テストを両方で使う。変更前にそのパスが既にあれば、新規追加として扱わない。両方の実行は同じランナー、依存関係、許可された資料、実行条件を使う。コピーと検証対象の対応を確定できない場合は未検証とする。
- `verify-diff` が、依頼 ID、前後のスナップショット ID、ケース資料の参照、実行件数と結果を記録する。有効な証拠は、その依頼で実際に実行した変更後 ID にだけ結び付く。台帳、依頼ごとの状態、ケース JSON、実行記録は作業ツリーの外にある Git 管理領域（`git rev-parse --git-path claude-verify` 配下）に置く。台帳行には ID と要約を置き、依頼の抜粋とケースの詳細は別ファイルに保存する。追記自体は検証した ID を変えない。
- Stop が呼ばれるたびに現在の ID と照合し、ホストが終了を確定した時点では最後の照合結果を使う。検証後に実装か追加テストが変われば、以前の証拠はその最終状態には使えない。追加ターンの枠を使っていれば「未検証」として終了する。

### 2.4 Verify 層の責務

- Verify の手順で参照する範囲は、依頼、対象リポジトリの製品コード・公開テスト・設定、利用者または実行器が明示した資料に限る。テストはその範囲から設計し、許可された資料を使った場合はケースに出典を残す。
- 開始時に公開テスト、共通 fixture、発見・実行設定の保護対象を確定し、`verify-diff` と終了時の証拠照合で内容とパスを確認する。Verify が加えるテストは新規追加のみ。既存 assertion の弱体化、削除、skip 化、ランナー設定による対象の縮小を含め、保護対象の変更があれば有効な証拠を発行しない。保護パスとランナーは対象リポジトリごとに明示する。
- 評価環境の可視範囲と採点器の隔離は評価リポジトリの責務とする（§4）。Verify の隔離コピーは比較実行用であり、評価用のサンドボックスは外側の実行器が用意する。

### 3.2 モード設定と自動テスト

v0.2 は `verifyV2` を明示したプロファイルに配備する。強制モードはプロファイル専用の `VL_CONFIG_DIR/config.json` に次を設定する。例のランナーとパスは fixture に合わせて選び、既存の設定と併存させる。

```json
{
  "verifyV2": {
    "mode": "enforce",
    "adversarial": false,
    "runner": "node",
    "protectedPaths": ["tests", "package.json"]
  }
}
```

`runner` は `node` または `pytest` の二択。Git の除外設定に該当する対象ファイルがある場合は、リポジトリ内のパスを任意設定の `includePaths` に列挙する。既存テストディレクトリを保護対象に含める場合は、開始時の既存ファイルを保護し、同じディレクトリへの新規テストファイルの追加を許す。設定を省いた場合の v0.2 は `off`。導入先の導入先では `observe` で始め、§3.3 の結果を確認した上で `enforce` に切り替える。

`node --test tests/verify-v02.test.js` で動作を確認し、リポジトリの既存テストも `node --test` で回す。

- 両ランナーで、後の assertion の実行と合格、および前の期待値不一致、入口不在、収集・依存エラー、前も合格を区別する。0 件、スキップ、assertion に到達しない成功、有効な証拠が得られない場合も確認する。
- 開始時からある編集・未追跡ファイル、未コミットの修正と新しいテスト、依頼中のコミットを含む状態で、比較に使った内容と記録の ID を照合する。台帳追記で証拠が失効せず、検証後に実装だけを直すと失効することを確認する。
- 既存 assertion の弱体化、設定による対象縮小、既存テストの削除を検出し、新規追加を許す。許可範囲外を指すリンクやテスト指定は証拠に使えないことを確認する。
- Stop の判定は、対象差分なし、ドキュメントのみ、有効な証拠あり、観察、強制、`stop_hook_active`、同一依頼での再入と次の依頼への切り替えを確認する。最終 ID が変わっても Verify による再ブロックがなく、「未検証」が残ることを確認する。

### 3.3 実セッションでの Stop hook 検証

実装セッションで、Claude Code と Codex のそれぞれに対し、書き捨ての dev fixture を用意する。観測用プロファイルでのみ強制設定を使い、Verify 単独と sample-harness の Stop hook 併用を試す。両方が継続を要求する場合は、設定上の順序を切り替えて観測する。

1. 依頼開始イベントが最初の編集より前に届き、利用者の次の依頼と hook による継続を区別できることを確かめる。ホストのバージョンと、Stop の入力に含まれる `stop_hook_active` の値を記録する。
2. 有効な証拠がない状態で終了させ、Verify の理由がモデルに届くこと、Verify が発生させた追加ターン数、他 hook を含む全体の継続回数を確認する。graph hook だけが先に継続した場合と、両 hook が同じ終了時に継続を求めた場合も確認する。
3. 追加ターンで検証して終了するケースと、検証後に実装を再変更して終了するケースを試す。さらに、同じホストセッションで次の利用者の依頼を送り、介入枠が新しくなることを確かめる。各ケースで最終 ID と台帳の「検証済み」または「未検証」を照合する。
4. 結果をホスト別に保存する。理由の配送、依頼ごとの上限、最終記録を確認できた構成で強制モードを有効にする。併用時の契約を確認できない構成は観察に留め、sample-harness には Verify のケース証拠を渡せるようにする。

### 3.4 dev スモークと P2 の差し替え

1. 評価側で独立に準備した同じ旧 dev 6 罠の公開 fixture と依頼を使う。各試行は新しい作業コピーとホストセッションから開始する。P0 は層なしとし、hook、verify スキル、checklist、Verify 用の指示と設定を取り除いたことを起動前に確認する。
2. P2 は Claude 用 `profiles-e1b` の `claude-verify-layer`、Codex 用 `profiles-e1b-codex` の `codex-verify-layer` をそれぞれ同名で v0.2 の配備内容に差し替える。両方に §3.2 の `enforce` と `adversarial: false` を設定し、fixture ごとに必要なランナーと保護パスを指定する。起動前にプロファイルのロード先、開始・Stop hook、モード、敵対段 off を確認する。
3. 各ホストで P0・P2 を旧 6 罠に各 1 回ずつ実行する（1 ホスト 12 試行）。発火、追加ターン数、前後の実行件数と結果、最終記録、時間と費用を取得する。公開された dev の例を一つ使い、選んだ境界だけに誤りを残した実装で追加テストが失敗することも確認する。このスモークは手順と計測の確認に使う。

## 4. 本評価

- 評価リポジトリは **P0（層なし）、P1（v0.1）、P2（v0.2 の強制モード・敵対段 off）** を同じ fixture、依頼、可視範囲、予算で実行する。P2 は §3.4 の同名プロファイルの差し替え方式で配備する。P2 のモードと敵対段 off は事前登録の追補で固定済み。Claude と Codex はホスト別に判定し、今回の P0 を比較基準に使う。
- 評価リポジトリの実行器は、全プロファイルと子プロセスが参照できる範囲を、依頼、対象の製品コード、公開テスト、明示した許可資料に制限する。隠しテスト、採点器、他試行の記録は作業環境の外に置く。外側で提出差分を採点し、既存の公開テスト・共通 fixture・実行設定を開始時点と比較して変更を検出する。新規テストの追加を許す。アクセス制限と採点器の保護を評価リポジトリで検証する。
- 有用性の判定は held-out の結果に基づく。各セル 3 試行とし、P0 の罠の合格率が 20〜80% の範囲外なら判定不能とする。有用の条件は P2 が P0 を上回ること、改善が後退を上回ること、対照の後退が 0、有効試行が 75% 以上であること。漏洩は無効、改ざんは不合格とし、差の信頼区間は副判定に使う。
- 共通の時間・費用の打ち切りは外側の実行器が適用する。ホストと試行の結果を集計する単位、分母、無効・打ち切り・再試行の扱い、予算値は、評価リポジトリの事前登録と追補を正本とする。本実行前に、評価側で架空の結果表を使って「有用」「基準未達」「判定不能」がホスト別に再現されることを確認する。

## 5. astra レビューからの変更

| 指摘 | rev2 での対応 |
|---|---|
| #1 証拠の契約 | ケースに依頼の該当箇所・入力・期待値を対応づけ、変更後の assertion 実行と合格を記録する。変更前の期待値不一致、入口不在、実行エラーを区別し、入口不在を境界の再現に数えない（§2.2） |
| #2 検証する木 | 依頼開始時の未コミット変更も含めて前を固定し、後は未追跡の対象ファイルを含む作業ツリーを採取する。同じ追加テストを両コピーで実行し、件数と結果を実行時の ID に結び付ける。台帳を作業ツリーの外に置く（§2.3） |
| #3 介入回数 | 追加ターンは依頼ごとに最大 1 回。最終 ID に証拠がなければ「未検証」。両ホストで `stop_hook_active` と他の Stop hook との併用を実セッションで確認する（§2.1、§3.3） |
| #4 層側の責務 | Verify の参照先を許可範囲に絞り、既存テスト・設定の保護を手順と検査に入れた。評価資産の隔離、外部採点、外側での差分検査は評価リポジトリが担う（§2.4、§4） |
| #5 評価条件 | P2 を両ホストで強制モード・敵対段 off に固定し、層なしの P0 と比較する。予算と集計は評価側の事前登録に従い、外側の実行器で確認する（§3.4、§4） |

非ブロッキング提案も採用した。最小版は一つの公開入口で一つの境界と期待値を検証し、fixture に必要な二つのランナーに絞る。旧 dev の罠は発火、証拠の記録、計測を確認するために使う。
