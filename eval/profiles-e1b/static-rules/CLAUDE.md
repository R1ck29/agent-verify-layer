# コミット前の確認項目

コミットする前に、今回の変更に当てはまる項目があれば、その確認を済ませてください。

- [escape-unescape-exact] 外部の形式（CSV・表計算・シェルなど）に安全に出すために、文字を足す・置き換える処理を入れたとき、読み戻す側が元の値に厳密に戻せるか。元の値がすでに同じ印や形を含んでいる場合でも、書いて読んだ結果が元と一致するかを、往復のテストで確かめる
  理由: 足した印と元からある同じ文字の区別がつかないと、読み戻しで利用者のデータが黙って書き換わる
  元の事故: wikiskill a10000d: レビューシートの往復で、' で始まる文字列が読み戻しで変わっていた
- [reject-before-write] 状態を書き換える処理（保存済みの記録・状態への代入）が、入力や呼び出し元の検査より後になっていないか。途中で拒否されたとき、すでに書き込んだ分が残らないか（検査をすべて終えてから書く、または失敗時に元へ戻す）
  理由: 検査の前に書き込むと、拒否された呼び出しの内容が、拒否後も記録に残る。CLI は失敗したときに保存しないので気づけず、ライブラリとして使うと状態が壊れる
  元の事故: sample-harness a10000a: 実行者でない人の提出が、拒否されたあとも実行中のノードに証拠として残っていた
- [caller-string-gate-variants] 呼び出し側から渡された文字列（ID・名前・ラベル）を、保存済みの値と比べて通す・拒否するを決める箇所は、同じ値の書き方の違いで判定が変わらないか。比較する前に値の形を揃える処理が、各所の素の比較ではなく一か所にまとまっているか
  理由: 素の文字列比較で決めた許可・拒否は、表記を少し変えるだけで抜けられ、守りたかった性質（別の者による確認など）が破れる
  元の事故: sample-harness a100003: 実行者と同じ ID でも、末尾の空白や大文字小文字を変えるだけで別人扱いになり、自分の作業を自分で確認して完了にできた
- [hook-input-failure-scope] hook が標準入力を読むとき、読み取りから解析までの失敗を、特定の例外 1 種類だけで受けていないか。入力が使えない場合の既定の動作（入力なしとして続行するか、止めるか）を決め、その段階で出うる例外を同じ扱いにする
  理由: 想定した失敗だけを拾う hook は、想定外の入力で hook の外へ例外を出し、止めてはいけない処理や判定まで巻き込む
  元の事故: sample-harness a100008: Stop hook が JSON の構文エラーだけを拾っていて、読み込み時の別の例外で hook ごと落ちた
- [concat-sources-overlap] 複数の出力源（メッセージ列・複数のフィールド・ログの断片など）を 1 つの文字列に連結しているとき、源どうしが同じ内容を重ねて持っていないか。想定した形のテスト用データだけでなく、実際に出力された生データの形で連結結果を作り、後段のパーサ（JSON など）に通して確かめる
  理由: 源が内容を重ねて持つと連結結果が二重になり、後段の解析が全件で静かに失敗する（例外は出ない）
  元の事故: llm-news a10000e: SDK のメッセージ列から回答を取り出す処理が同じ文章を二重に連結し、JSON が全件で読めなかった
- [status-set-single-source] ノードの状態を文字列と直接比べる条件を足すとき、「その先へ進めてよい（済んだ）状態」の集合を 1 か所で決めた定数を使っているか。状態が増えたとき、手書きの比較だけが取り残され、もう動かないものを待ち続ける表示や判定になる
  理由: 状態の比較が何か所かに散らばると、状態を足したときに 1 か所だけ古いまま残り、誰も気づかない
  元の事故: sample-harness a100009: 依存先の判定を 1 か所だけ手書きの比較で残していて、置き換えられた依存先を待ち続けるよう案内していた
- [hooks-stdout] モデルや利用者に届けたい通知が stdout（または JSON の出力）に出ているか。stderr に出した通知は、止めない hook では debug ログにしか出ない
  理由: stderr に出した通知は、モデルにも利用者にも届かない
  元の事故: strategic-compact の通知が約 4 か月 stderr に出ていた
- [flaky-test-hiding] flaky なテストを、skip・sleep・通るまでの再試行で隠していないか。原因が分からなければ削除し、理由をコミットメッセージに書く
  理由: 隠した flaky は、本物の不具合を見えなくする
  元の事故: 検証に関する記事の規則
