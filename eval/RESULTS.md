# 評価 E1（縮小版）の結果

**状態: 未実施**（2026-11-18 時点。評価一式の準備と、モデルを呼ばない範囲の確認だけが済んでいる）。試行は、ログイン済みの外側のシェルで `./run-eval.sh smoke` → `./run-eval.sh full` として実行し、集計と下の「結果」欄は、その後に埋める。

## 事前に固定した判定基準（結果を見る前に、この節を書いた。結果を見たあとは書き換えない）

### 単位

- 試行の合否 = 隠しテストの合否（主）。タスクごとに、プロファイル別の「隠しテストに合格した試行の数（2 回中）」を数える
- タスクの**改善**: P2 の合格数 > 比べる相手（P0 か P1）の合格数。**後退**: P2 < 相手。同じなら変化なし
- 集計から外れる試行（`valid: false`。認証・レート制限・ネットワークなどの環境起因）は、その数を報告する。同じタスクの 2 回のうち 1 回しか有効でないときは、そのタスクを比べない

### 判定

| 結論 | 条件 |
| --- | --- |
| **有用** | P2 が P0 より、**罠のタスクで 改善 > 後退**、かつ **対照のタスクで 後退 0** |
| **有用でない** | 上を満たさない（罠で 改善 ≦ 後退、または対照で後退が 1 つでもある）。ただし下の「判定不能」に当たるときは判定不能 |
| **判定不能** | 次のどれか: (a) P0 の罠の合格率が 7/8 以上（天井で、改善の余地がない）、(b) P2 の罠の試行 8 回のうち、チェックリストの項目が 1 回も発火していない（効く機会がなかった。台帳の `fired` で数える）、(c) 有効な試行が全体の 75% 未満 |

追加の読み方（判定とは別に書く）:

- **P2 が P1 より良くないなら**（罠のタスクで、P2 の P1 に対する 改善 ≦ 後退）、「この層のうち、チェックリストの注入は CLAUDE.md で代替できる」と書く。P2 が P1 より良いときも、その差には P2 だけが持つ Rules の 2 行が混ざっていることを書く
- 台帳（観察）だけの価値は合格率では測れない。別に、次の 2 つを報告する（P2 の試行のみ）:
  1. **台帳がコミットを拾えた割合**: 台帳の commit 行の数 ÷ エージェントが作ったコミットの数（作業ツリーの `git rev-list --count HEAD` − 1）
  2. **台帳の結果が実態と合う割合**: トランスクリプトから決める「実態」と、台帳の commit 行の `result` を並べる。実態は次の 4 つ:
     - A: `Skill(verify)` を呼んでいない → 台帳は `none` が正しい
     - B: `Skill(verify)` のあとに、Edit / Write がない → `verified` が正しい
     - C: `Skill(verify)` のあとに Edit / Write があり、**最後の Edit / Write のあとに、テストを実行する Bash（`unittest`）がある** → 実態は「編集後に確認した」。台帳が `stale` なら**偽の stale**（docs/SMOKE.md 2 回目の実例。始めた時点のツリーを記録する設計の限界）
     - D: `Skill(verify)` のあとに Edit / Write があり、そのあとにテストの実行がない → `stale` が正しい
     また、Skill を呼ばずに `unittest` を Bash で直接実行した試行（SMOKE.md 1 回目と同じ型）の数を報告する（台帳は `none`。この層からは区別できない）

### 副次の指標（判定には使わない）

- プロファイル別・罠／対照別の合格率（隠しテスト）。ターン数と費用の差（P2 − P0、P1 − P0。中央値と、タスクごとの差の向き）
- verify の呼び出し率（`Skill(verify)` を 1 回でも呼んだ試行の割合）と、最後の `git commit` より前だった割合（参考指標のグレーダー）。**最初の編集より前に verify を呼んだ割合**（`verify_before_first_edit=1`）: そのとき diff は空で、チェックリストは当たらない
- 罠ごとの、不合格の理由（隠しテストの `FAIL …` の行）。再発した不具合が、元の不具合と同じ型かを、数件読んで確かめる

### 限界（結果の前に書く）

- n が小さい: タスク 8、1 セルあたり 2 試行。タスクごとの改善・後退は 0 か 1 回の違いで動く。区間や検定は付けない（付けても、読める幅にならない）。**この評価で「有用」と出ても配備の根拠としては弱く、「有用でない」と出ても「効かない」の証明にはならない**
- チェックリストの正規表現は、罠を知ったうえで書いた（CASES.md）。実際の導入では、発火はこれより少ない
- fixture は小さな合成のライブラリで、実際のハーネスのコードではない。モデルは sonnet 1 つ
- P2 の効きは、Claude が **verify を、編集のあとに呼んだとき**にだけ出る。呼ばない、または編集の前に呼ぶ（SMOKE.md の 2 回目）と、チェックリストは当たらない。これはこの層の設計の性質であり、評価の欠陥ではない
- 隠しテストは、参照解 2 通りでしか検証していない。不合格の理由を数件読む

## E2（`/code-review` の再現率）を今回やらない理由

詳細は [README.md](README.md)。要点: (1) 正例が 4 件で、設計が採否を決めるとした 20 件に届かない。(2) E2 が測るのは同梱の `/code-review` と CLAUDE.md の節で、この層（v0.1）が配るものではない。(3) 実際のバグの正解キーが足りず、合成で埋めると再現率が高めに出る。同じ fix コミットを使い回すと E1 との独立性もない。(4) 費用: E1 の 48 試行に足すと上限（30 USD）を超えうる。E2 は、正例が増えてから別の評価として行う。

## 結果

**状態: 実施済み**（2026-11-18、full 48 試行。上部の「状態: 未実施」と判定基準は、事前固定の時点の記述で、書き換えていない）。数値はすべて `tools/aggregate.py` が、試行のファイル（`trials.jsonl`、各試行の `stdout.jsonl`、P2 の workdir の台帳 `.git/claude-verify/ledger.jsonl`）から計算したもの。生の値は [results/e1-full-aggregate.json](results/e1-full-aggregate.json)。再現: `python3 -I tools/aggregate.py ../../eval-out/full/20261118-203822-800-2c --json results/e1-full-aggregate.json`。

実施の条件: sonnet（claude-sonnet-5-5）、Claude Code 2.1.327、48 試行すべて有効（環境起因で外れた試行 0、評価の中身（`checks/`・`reference/`）を読んだ形跡のある試行 0）。費用はすべて `client_estimate`（API 単価での推定。3 プロファイルの合計は約 3.45 USD で、上限 30 USD の内）。

### 台帳（P2 のみ、16 試行）

- **拾えた割合**: 台帳の commit 行 16 ÷ エージェントのコミット 16 ＝ **16/16**（verify を呼ばなかった 4 試行でも、commit 行は `none` として残った）
- **結果の合致**（事前の定義: 編集は Edit / Write だけを数える）: **13/16**。A（verify を呼んでいない）4 件はすべて `none` で合致。B 10 件のうち 9 件が `verified` で合致、1 件は `stale`（`ctrl-format-size` の 2 回目: 編集の後ろのテスト追加が Bash の python 経由で、定義の外）。C 2 件はどちらも `stale` ＝ **偽の stale 2 件**（verify を編集の前に読み込み、編集のあとにテストを実行していた。SMOKE.md 2 回目と同じ型）。D は 0 件
- 参考（事前の定義の外、推測を含む）: Bash での書き込み（heredoc、リダイレクト、`sed -i`、python の write）も編集と数えると、上の B の 1 件は D（`stale` が正しい）になり、合致は **14/16**。偽の stale は変わらず 2 件。正規表現による推定なので、判定には使わない
- **Skill を経由せず直接実行**: P2 で 4 件（`trap-locale-decode` 2、`trap-drift-scope` 2。いずれも台帳は `none`。この層からは「検証していない」と「Skill を使わずに検証した」が区別できない）
- **チェックリストが発火した罠の試行**: 8 回のうち 4 回（`trap-fifo-bounded-read` 2、`trap-rejection-leak` 2）。残り 4 回（`trap-locale-decode`、`trap-drift-scope`）は verify を呼ばなかったので、台帳に run 行がなく、発火の機会がなかった

### 判定: **判定不能**

事前の基準の (a) に当たる: **P0 の罠の合格率が 8/8（7/8 以上）**で、天井。改善の余地がなかった。(b)（P2 の罠で一度も発火しない）と (c)（有効な試行が 75% 未満）には当たらない。

判定不能のとき、上の「判定」の表の規則を機械的に当てはめると、罠で 改善 0 < 後退 1、対照で後退 0 なので「有用でない」側に出る。ただし (a) が優先するので、**有用とも有用でないとも言えない**。この結果は、この層が効かないことの証明ではなく、効くことの根拠でもない。

### 所見

- **罠のタスクが、この評価では難しくなかった**: P0 は、チェックリストも何もない状態で罠 4 件を 8/8 通した。P1（全項目を CLAUDE.md に書いた）も 8/8。つまり、sonnet はこの 4 つの小さな fixture では、不具合を自分で避けた。層の効果を測るには、P0 の合格率が下がる罠（難しい fixture、実際のコード）が要る
- **P2 の唯一の後退は `trap-drift-scope`（2 回とも不合格）**: 不合格の理由は 2 回とも同じ（`third-party-after-ours`: 他者の hook が自分の hook のあとに並んでいるとき、`check` が False を返す）。コードを読むと、2 回とも「自分の hook が末尾にあること」を条件に足していた（P0 の実装は、自分の hook だけを取り出して比べる）。元の不具合（sample-harness a100005: ずれの検査を、文書全体との一致で書く）と同じ型の再発。**この 2 回は、どちらも verify を呼ばず、`unittest` を直接実行してコミットした**ので、層の hook は走っておらず（台帳は `none`）、層が直接この結果を悪くしたとは言えない。原因は、標本のばらつき（n=2）か、P2 だけが持つ Rules の 2 行か、見分けられない。**分かっているのは、後退が 1 タスクで 2 回続いたことだけ**
- **P2 が P1 より良くないか（追加の読み方）**: 罠で P2 の P1 に対する 改善 0 ≦ 後退 1。基準の文言どおりなら「この層のうち、チェックリストの注入は CLAUDE.md で代替できる」と書く場面。ただし P1 も P0 も天井で、注入が効くかを見る余地がそもそもなかったので、**「代替できる」とも「できない」とも、この評価では示せていない**。P2 と P1 の差には、P2 だけが持つ Rules の 2 行が混ざる（README）
- **verify の呼び出しは、層の有無と関係なく高い**: fixture のプロジェクトに verify スキルがあるため、P0 でも 11/16 で呼ばれた。層が加えたのは台帳と、当たった項目の注入だけで、verify を呼ぶ行動そのものは変わっていない（P0 11/16、P2 12/16）
- **層が効く機会は、verify を呼ぶかで決まる**: 罠 8 回のうち、P2 は 4 回しか verify を呼ばなかった。呼ばなかった 4 回は、`trap-locale-decode`（合格）と `trap-drift-scope`（不合格）。P0・P1 は罠で、それぞれ 3 回・5 回しか呼ばず、残りは直接実行だった。直接実行だと、この層（v0.1）は何もできない
- **偽の stale は、2/16 で、編集の前に verify を読み込んだ試行に出た**。数は少ないが、SMOKE.md の実例と同じ型で、次の版の 1・4 に当たる

### 限界（結果を見たうえで追加）

- 上に書いた事前の限界のすべて（n が小さい、チェックリストの正規表現は罠を知って書いた、合成の fixture、モデルは 1 つ）に加え、**天井**のため、層の効果の有無はこの評価では測れていない。有用でない、とも言えない
- 台帳の「結果の合致」の定義は、Edit / Write だけを編集と数える。実際は、Bash の heredoc などでファイルを書く試行が多く、偽の stale・D の数え方に影響する（上の参考値）。定義は結果を見たあとも変えていない
- P2 の不合格 2 件は、1 タスクの 2 回。同じ原因かは、トランスクリプトとコードを読んだ範囲でしか言えない

## 次の版（v0.2 の候補。v0.1 の判定ロジックはこの作業では変えていない）

docs/SMOKE.md の 2 回の実機スモークで見えた、台帳の実態との食い違いに対する改善案。評価の結果を見て、優先順位を決める。

1. **「検証が走った時点」のツリーを記録する**: `Skill(verify)` の開始時ではなく、そのあとに最初に実行された verify のコマンドの Bash（`.claude/skills/verify/SKILL.md` に書かれたコマンド、または利用者が設定したパターン）の PostToolUse で、ツリーを取り直す。偽の stale（実態は編集後に確認済み）が減る。SKILL.md の解釈が要るので、まず `skipGlobs` と同様の、リポジトリ側の簡単な設定（`verifyCommands`）から
2. **Skill を経由しない直接実行を、別の行として残す**: SKILL.md のコマンドが Bash で直接実行されたら `kind: run, via: bash-direct` として記録し、commit の結果は `verified` と混ぜず、`verified-direct` のように分ける（SMOKE.md 1 回目: 実態は検証済みでも `none` になった）
3. **チェックリストを、編集のあとにも渡す**: verify を編集の前に読み込むと、そのときの diff は空でチェックリストが当たらない。`PreToolUse(Bash git commit)` で、当たった項目を `additionalContext` として渡す（観察モードのまま、止めない）。評価で `verify_before_first_edit` が高ければ、最優先
4. **stale の判定を、確認の実行時点に対して行う**（1 とセット）: 「確認のあとに、コミットされるファイルが変わったか」だけを見る
5. 評価の側: 隠しテストを、別の正しい実装・誤った実装でも検証する（今は参照解 2 通り）。罠を増やす前に、4 件の結果の読み方（不合格の理由）を確かめる

### 評価を見たあとの優先順位（仮説。この評価では確かめていない）

- P2 の罠 8 回のうち 4 回は verify を呼ばず、直接実行でコミットした。この層は、その 4 回に何もできなかった（台帳は `none`）。したがって **3（`git commit` の直前に、当たった項目を渡す）と 2（直接実行を別の行で残す）** を先にする。verify を最初の編集の前に呼んだ割合は 2/16 と低いので、3 の理由は「編集の前の verify」より「verify を呼ばない試行」のほうが大きい
- 偽の stale は 2/16。1 と 4 は、その次
- 評価の側が先: 罠が難しくなく、P0 が天井だった。次に評価をするときは、P0 の合格率が 7/8 を下回る罠（実際のコード、または fixture を大きくする）を用意してから回す
