# 評価 E1（縮小版）の結果

**状態: 未実施**（2026-11-18 時点。評価一式の準備と、モデルを呼ばない範囲の確認だけが済んでいる）。試行は、ログイン済みの外側のシェルで `./run-eval.sh smoke` → `./run-eval.sh full` として実行し、集計と下の「結果」欄は、その後に埋める。

## 事前に固定した判定基準（結果を見る前に、この節を書いた。結果を見たあとは書き換えない）

### 単位

- 試行の合否 = 隠しテストの合否（主）。タスクごとに、プロファイル別の「隠しテストに合格した試行の数（2 回中）」を数える
- タスクの**改善**: P2 の合格数 > 比べる相手（P0 か P1）の合格数。**後退**: P2 < 相手。同じなら変化なし
- 集計から外れる試行（`valid: false`。認証・レート制限・ネットワークなどの環境起因）は、その数を報告する。同じタスクの 2 回のうち 1 回しか有効でないときは、そのタスクを比べない

### 判定

| 結論 | 条件 |
| --- | --- |
| **有用** | P2 が P0 より、**罠のタスクで 改善 > 後退**、かつ **対照のタスクで 後退 0** |
| **有用でない** | 上を満たさない（罠で 改善 ≦ 後退、または対照で後退が 1 つでもある）。ただし下の「判定不能」に当たるときは判定不能 |
| **判定不能** | 次のどれか: (a) P0 の罠の合格率が 7/8 以上（天井で、改善の余地がない）、(b) P2 の罠の試行 8 回のうち、チェックリストの項目が 1 回も発火していない（効く機会がなかった。台帳の `fired` で数える）、(c) 有効な試行が全体の 75% 未満 |

追加の読み方（判定とは別に書く）:

- **P2 が P1 より良くないなら**（罠のタスクで、P2 の P1 に対する 改善 ≦ 後退）、「この層のうち、チェックリストの注入は CLAUDE.md で代替できる」と書く。P2 が P1 より良いときも、その差には P2 だけが持つ Rules の 2 行が混ざっていることを書く
- 台帳（観察）だけの価値は合格率では測れない。別に、次の 2 つを報告する（P2 の試行のみ）:
  1. **台帳がコミットを拾えた割合**: 台帳の commit 行の数 ÷ エージェントが作ったコミットの数（作業ツリーの `git rev-list --count HEAD` − 1）
  2. **台帳の結果が実態と合う割合**: トランスクリプトから決める「実態」と、台帳の commit 行の `result` を並べる。実態は次の 4 つ:
     - A: `Skill(verify)` を呼んでいない → 台帳は `none` が正しい
     - B: `Skill(verify)` のあとに、Edit / Write がない → `verified` が正しい
     - C: `Skill(verify)` のあとに Edit / Write があり、**最後の Edit / Write のあとに、テストを実行する Bash（`unittest`）がある** → 実態は「編集後に確認した」。台帳が `stale` なら**偽の stale**（docs/SMOKE.md 2 回目の実例。始めた時点のツリーを記録する設計の限界）
     - D: `Skill(verify)` のあとに Edit / Write があり、そのあとにテストの実行がない → `stale` が正しい
     また、Skill を呼ばずに `unittest` を Bash で直接実行した試行（SMOKE.md 1 回目と同じ型）の数を報告する（台帳は `none`。この層からは区別できない）

### 副次の指標（判定には使わない）

- プロファイル別・罠／対照別の合格率（隠しテスト）。ターン数と費用の差（P2 − P0、P1 − P0。中央値と、タスクごとの差の向き）
- verify の呼び出し率（`Skill(verify)` を 1 回でも呼んだ試行の割合）と、最後の `git commit` より前だった割合（参考指標のグレーダー）。**最初の編集より前に verify を呼んだ割合**（`verify_before_first_edit=1`）: そのとき diff は空で、チェックリストは当たらない
- 罠ごとの、不合格の理由（隠しテストの `FAIL …` の行）。再発した不具合が、元の不具合と同じ型かを、数件読んで確かめる

### 限界（結果の前に書く）

- n が小さい: タスク 8、1 セルあたり 2 試行。タスクごとの改善・後退は 0 か 1 回の違いで動く。区間や検定は付けない（付けても、読める幅にならない）。**この評価で「有用」と出ても配備の根拠としては弱く、「有用でない」と出ても「効かない」の証明にはならない**
- チェックリストの正規表現は、罠を知ったうえで書いた（CASES.md）。実際の導入では、発火はこれより少ない
- fixture は小さな合成のライブラリで、実際のハーネスのコードではない。モデルは sonnet 1 つ
- P2 の効きは、Claude が **verify を、編集のあとに呼んだとき**にだけ出る。呼ばない、または編集の前に呼ぶ（SMOKE.md の 2 回目）と、チェックリストは当たらない。これはこの層の設計の性質であり、評価の欠陥ではない
- 隠しテストは、参照解 2 通りでしか検証していない。不合格の理由を数件読む

## E2（`/code-review` の再現率）を今回やらない理由

詳細は [README.md](README.md)。要点: (1) 正例が 4 件で、設計が採否を決めるとした 20 件に届かない。(2) E2 が測るのは同梱の `/code-review` と CLAUDE.md の節で、この層（v0.1）が配るものではない。(3) 実際のバグの正解キーが足りず、合成で埋めると再現率が高めに出る。同じ fix コミットを使い回すと E1 との独立性もない。(4) 費用: E1 の 48 試行に足すと上限（30 USD）を超えうる。E2 は、正例が増えてから別の評価として行う。

## 次の版（v0.2 の候補。v0.1 の判定ロジックはこの作業では変えていない）

docs/SMOKE.md の 2 回の実機スモークで見えた、台帳の実態との食い違いに対する改善案。評価の結果を見て、優先順位を決める。

1. **「検証が走った時点」のツリーを記録する**: `Skill(verify)` の開始時ではなく、そのあとに最初に実行された verify のコマンドの Bash（`.claude/skills/verify/SKILL.md` に書かれたコマンド、または利用者が設定したパターン）の PostToolUse で、ツリーを取り直す。偽の stale（実態は編集後に確認済み）が減る。SKILL.md の解釈が要るので、まず `skipGlobs` と同様の、リポジトリ側の簡単な設定（`verifyCommands`）から
2. **Skill を経由しない直接実行を、別の行として残す**: SKILL.md のコマンドが Bash で直接実行されたら `kind: run, via: bash-direct` として記録し、commit の結果は `verified` と混ぜず、`verified-direct` のように分ける（SMOKE.md 1 回目: 実態は検証済みでも `none` になった）
3. **チェックリストを、編集のあとにも渡す**: verify を編集の前に読み込むと、そのときの diff は空でチェックリストが当たらない。`PreToolUse(Bash git commit)` で、当たった項目を `additionalContext` として渡す（観察モードのまま、止めない）。評価で `verify_before_first_edit` が高ければ、最優先
4. **stale の判定を、確認の実行時点に対して行う**（1 とセット）: 「確認のあとに、コミットされるファイルが変わったか」だけを見る
5. 評価の側: 隠しテストを、別の正しい実装・誤った実装でも検証する（今は参照解 2 通り）。罠を増やす前に、4 件の結果の読み方（不合格の理由）を確かめる
